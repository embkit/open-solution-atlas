# 00-context / 利益相关方

## 1. 组织

| 组织 | 职责 | 系统关系 |
|---|---|---|
| **医院/医疗机构**（医疗卫生机构） | 运营平台；对数据安全和个人信息保护承担**主体责任** | 所有方/运营方；向卫生健康行政部门负责 |
| **医院领导组**（网络安全和信息化工作领导小组） | 由主要负责人担任组长；实行第一责任人/直接责任人机制 | 对数据和安全拥有治理权 |
| **医院信息部门**（信息科） | 建设并运营 HIS/EMR | 运营平台；不具备临床权限 |
| **临床科室** | 生成临床病历；决定临床内容 | 临床病历的主要作者 |
| **病案/医务部门**（病案科） | 编码、DRG/DIP、完整性、归档 | 负责编码后的记录；同时使用两类权威记录 |
| **药剂科** | 药品调配、用药安全 | 接收 CPOE 医嘱并进行核对与报告 |
| **护理部** | 护理记录、执行记录 | 诊疗记录的作者和执行者 |
| **财务/收费部门**（财务/收费处） | 收费项目、结算、成本 | 使用就诊/诊疗活动；**绝不修改临床病历** |
| **医保职能部门**（医保办） | 医保结算、合规、接口 | 使用方/评估方；记录相互分离 |
| **实验室（LIS）** | 标本、分析、结果 | 上游结果生产者 |
| **放射/影像科（RIS/PACS）** | 影像采集、判读 | 上游生产者；DICOM 边界 |
| **公共卫生/疾控接口**（疾控/公卫） | 法定传染病报告、登记 | 下游法定使用方 |
| **区域健康信息平台** | 跨机构交换 | 对等交换方 |
| **卫生健康行政部门/监管机构** | 监督、检查、评级 | 外部监管机构；指定等保等级 |
| **网络安全/隐私职能部门** | 访问控制、审计、保留期、事件响应 | 约束每项能力 |
| **研究/生物样本库部门** | 临床数据二次利用 | 在不同规则下作为下游使用方 |
| **患者/公众** | 数据主体 | 权利主体；同意机制得以存在的原因 |

## 2. 角色（应用参与者）

| 角色（英文） | 中文 | 关键权限/任务 |
|---|---|---|
| Registration clerk | 挂号员 | 创建挂号记录、解析 EMPI、标记疑似重复档案 |
| Physician / clinician | 医师 | 编写医嘱和病程记录、签署文书、添加补录 |
| Nurse | 护士 | 记录护理情况、执行情况和生命体征 |
| Pharmacist | 药师 | 审核并调配药品、检查药物相互作用 |
| Imaging radiologist | 影像诊断医师 | 判读检查、出具 DiagnosticReport |
| Lab technologist | 检验技师 | 生成并验证结果 |
| Medical record coder | 病案编码员 | 使用编码体系与版本分配 ICD/操作编码 |
| Medical affairs / DRG-DIP manager | 病案/医保管理人员 | 完整性、编码审计、支付分组 |
| Billing clerk | 收费员 | 收费、退款、对账——仅依据收费/结算记录 |
| Insurance specialist | 医保专员 | 结算、合规检查、接口操作 |
| Privacy officer / 数据安全负责人 | 数据安全负责人 | 数据分类、重要数据识别、风险评估 |
| Compliance auditor | 个人信息保护合规审计员 | 定期审计（依据行业规则） |
| HIM administrator | 系统管理员 | 管理账户和配置；**不具有**临床内容权限 |
| Security administrator | 安全管理员 | 安全配置；独立于系统管理 |
| Break-glass approver | 紧急访问审批人 | 授权并复核紧急访问 |
| Patient / proxy | 患者/代理人 | 行使信息权利；同意 |

### 非人类参与者

| 参与者 | 说明 |
|---|---|
| **EMPI / MPI 服务** | 患者身份解析；**合并和拆分，并留有审计记录**（`AGENTS.md`） |
| **临床数据存储** | 临床事实的权威记录；仅追加和补录，不得原地编辑已签署内容 |
| **文档/签署服务** | 署名、签署和补录关联 |
| **术语服务** | 版本化 ICD/LOINC/SNOMED 映射（`AGENTS.md`） |
| **编码服务** | 分配编码并记录编码体系与版本；为病案提供数据 |
| **收费引擎** | **从**就诊/诊疗活动派生收费项目；**仅写入收费/结算记录** |
| **医嘱/计算引擎（CPOE）** | 医嘱、核查、结果关联 |
| **DICOM/PACS 网关** | 影像边界 |
| **LIS/RIS 接口** | 多数部署中采用 HL7 v2.x 消息传递 |
| **同意与披露管理器** | 针对敏感信息取得单独同意；披露控制 |
| **审计追踪服务** | 谁在何时、基于何种授权访问了什么 |
| **数据分类服务** | 核心/重要/一般数据分类，驱动差异化保护 |
| **AI/算法服务** | L3 界面——受明确约束管控，绝不采用直接基于病历生成自由文本的模型 |

## 3. 外部/上游—下游系统作为参与者

- **区域健康信息平台**——跨机构交换。
- **国家卫生信息互联系统**——部署环境存在此类系统时。
- **医保结算平台**——**独立的**记录边界。
- **公共卫生报告系统**——法定报告。
- **实验室和影像系统**——LIS/RIS/PACS。
- **药房自动化系统**——调配与药柜。
- **血库、ICU 设备和床旁监护仪**——设备生成的临床数据。
- **支付网关**——行政性收费收取。
- **研究平台/生物样本库**——二次利用，适用不同规则。
- **身份提供方/员工目录**——员工身份验证。
- **安全监控/SIEM**——接收审计与安全遥测数据。
- **备份、归档和灾难恢复**——可用性与证据留存。

## 4. 参与者目标（主要）

- **临床医师**：在诊疗现场一次录入记录，不让系统中断诊疗；并能更正先前的病程记录，而不必担心破坏原记录。
- **患者**：了解谁查看过自己的病历，并看到更正记录，而不是无声更改。
- **编码/病案管理人员**：编码应反映实际发生的事项，并记录术语版本，以便未来进行重新映射。
- **收费**：结算经得起审计——通过从就诊/诊疗活动派生数据实现，绝不通过编辑就诊/诊疗活动实现。
- **数据安全负责人**：了解病历的每一份副本存放于何处、谁可以访问，并证明访问已获得授权。
- **信息部门**：在诊疗期间保持平台可用，并确保临床病历与收费/结算记录即使在压力下也真正分离。
- **研究人员**：访问去标识化或已取得同意的数据，同时避免研究成为失控的披露渠道。
- **监管机构**：提供证据，证明分级、保留期和重要数据处理与所声明内容一致。

> ⚠️ ASSUMPTION: 本方案包假定**临床病历是临床事实的权威来源**，**收费/结算记录是收费项目的权威来源**。二者对保障范围问题存在冲突时，收费/结算记录决定应付费用，临床病历决定实际发生的事情。这是对 `AGENTS.md` 分离规则的解读，而非直接引述的规则。
