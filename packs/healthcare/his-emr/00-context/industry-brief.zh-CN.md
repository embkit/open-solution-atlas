# 00-context / 行业简报——医院信息系统与电子病历

## 1. 这套系统在价值链中的位置

医疗服务由人提供；而对"发生了什么"的记录，使其可辩护、可比较、可报销。
**HIS/EMR** 就是承载这份记录的系统——一位患者一次就诊的临床真相——并把它与
周边的一切连接起来：医嘱、结果、影像、药房、计费与医保。

```
   患者 / 临床人员                      下游
   ───────────────────                 ──────────
   挂号登记  (ADT)                      计费与医保 (医保结算)
   医嘱  (CPOE)                         报表与统计 (病案)
   病历记录 / 生命体征                  研究与登记
   护理 / 药房                           区域健康信息交换
   检验 (LIS) · 影像 (RIS/PACS/DICOM)    公共卫生报送
              │                                ▲
              ▼                                │
   ┌──────────────────────────────────────────┴─────────────────────────┐
   │  HIS / EMR                                                          │
   │                                                                    │
   │  身份：EMPI (企业主索引)——合并 / 拆分，且可审计                      │
   │  临床：Patient · Encounter · Observation · MedicationRequest …     │
   │  文书：已签署记录，只能追加附录，不得原地修改                        │
   │  术语：ICD-10/11、LOINC、SNOMED——带版本映射的服务                    │
   │  边界：影像用 DICOM，消息交互用 HL7 v2/FHIR                          │
   └────────────────────────────────────────────────────────────────────┘
              │                                    ▲
              ▼                                    │
   计费与医保（独立记录）                     遗留与科室系统
```

`AGENTS.md` 给出了本方案包的第一条铁律：**把临床记录与计费/医保记录分开——临床
真相绝不为了让计费满意而被修改。** 下面的一切都源于这一分离是架构性的，而不
仅仅停留在概念层面。

## 2. 决定架构的那条分离

| | 临床记录 | 计费/医保记录 |
|---|---|---|
| 用途 | 患者身上发生了什么 | 欠了什么，由谁欠 |
| 可变性 | 追加 + 附录；绝不为了迁就编码而被修改 | 随规则变化重新计算 |
| 词汇 | 临床术语 + ICD/LOINC/SNOMED | 收费编码、政策规则、支付方格式 |
| 出错后果 | 伤害患者 | 付款争议 |
| 归口 | 临床科室 | 财务/医保职能 |

> 一份同时服务两种用途的记录，总会被朝压力更大的那一侧编辑，而压力永远来自
> 计费。这条分离不是整洁癖——它是一份能被临床信任的记录与一份不能被信任的记录
> 之间的差别。

## 3. 以 FHIR 建模，在影像边界上使用 DICOM

`AGENTS.md` 要求临床数据以 **HL7 FHIR 资源**建模，而不是随意设计的表结构，
并**以 DICOM 作为影像边界**。

由此形成三层，每一层的变更纪律各不相同：

| 层 | 承载什么 | 为什么用这个模型 |
|---|---|---|
| **临床核心** | Patient、Encounter、Observation、MedicationRequest、Condition、Procedure、AllergyIntolerance、DiagnosticReport、DocumentReference | FHIR 资源语义给出的是可交换、带版本的临床词汇，而不是某一家医院的表形状 |
| **影像** | DICOM 对象、检查、序列、设备类型、PACS/RIS | 影像有自己成熟的、由设备类型驱动的对象模型；硬塞进关系表会不可逆地丢失信息 |
| **遗留互操作** | HL7 v2.x 消息（ADT、ORM、ORU） | 多数科室系统与区域平台今天真正讲的语言 |

> ⚠️ ASSUMPTION：本方案包给出 FHIR 资源的**名称**，但不主张某个规范版本。
> R4 与 R5 存在差异，选用哪一个是记录在 `SOURCES.md` §2 中的方案包决策，
> 而不是本简报可以断言的事实。

## 4. 身份：EMPI 是承重结构，而且可以反向纠错

患者身份是一切临床事实的根。本方案包认真对待由此带来的两个后果：

- **合并与拆分必须同时存在，并且都必须被审计。** 重复患者会悄然割裂一段病史；
  一次错误合并会悄然把两个人的人生拼在一起。一个只能合并而不能拆分的平台，
  已经替一个人做了不可逆的决定（`AGENTS.md`）。
- **身份归并是概率性的，而这个概率必须可见。** 隐藏自身不确定性的匹配阈值，
  会产出没有人能安全纠正的记录。

## 5. 已签署文书：只加附录，绝不修改

`AGENTS.md` 要求**对已签署临床文书的每一次修订都是附录，绝不是原地修改**。

这与 `workflow-bpm` 方案包的审计轨迹是同一个原则，只是用到了临床著录上：一份
已经签署的记录，是某个时点上"当时怎么想"的证据。原地更正会同时毁掉证据与
临床记录。更正的做法是新增一条署明作者、带时间戳、引用原件的附录。

## 6. 术语是一项带版本的服务，不是一张查找表

ICD-10/ICD-11、LOINC 与 SNOMED 都会随时间演进，编码会被**停用**、**替换**
和**重新映射**。在实施时一次性建立的映射，会悄然变成错误。

`AGENTS.md` 要求术语映射是一项**带版本的服务**：每一条带编码的临床事实都记录
它所依据的编码体系**及其版本**，而重新映射是一次带版本、可审计的操作，而不是
一次无声的升级。

## 7. 核心流程（L1 视角）

1. **登记与识别**——ADT；创建或解析 EMPI；关联或标记疑似重复记录以供对账。
2. **就诊**——入院/挂号，指派到诊疗上下文，开启就诊记录。
3. **医嘱**——CPOE：下达医嘱（药品、检验、影像），并附上临床决策。
4. **结果**——结果从 LIS 或 RIS/DICOM 返回，登记到对应的医嘱与就诊之下。
5. **文书**——病历、报告与出院小结被撰写、**签署**，此后只能以附录方式修订。
6. **编码**——诊断与操作按带版本的术语编码；编码后的记录同时（分别）供临床
   记录与计费使用。
7. **计费与结算**——计费从就诊记录推导费用，**且不修改临床记录**。
8. **交换与报送**——区域交换、公共卫生报送、研究。

## 8. 为什么这套系统格外难做对

- **一个患者，两种真相。** 临床记录与计费记录会不一致。哪一个才是对的，是一个
  政策问题，而且答案并不总是"临床那个"。
- **术语的腐坏是无声的。** 上游已停用的编码仍会在多年后出现在存量记录里；重新
  映射是一次带临床风险的迁移，而不是一次查表。
- **最难的数据恰恰是监管最严的。** 基因组、生物识别、跨境与研究用途，各自在
  基线之上触发不同的规制体系。
- **临床可用性高于一致性。** 一个因为接口故障就拒绝收治患者的平台会造成伤害；
  每一种可用性设计都要在一致性上让出些什么，而这份让步必须写明。
- **签署不等于身份认证。** 签署意味着合法性；本方案包把二者当作两种不同的
  能力，因为把它们混为一谈，正是"已认证"变成一个没有明确所指之词的途径。

## 9. 质量指标的定义

L1 给出意图；阈值在 L2 成为 NFR 目标。

| 指标 | 它回答什么 |
|---|---|
| 编码完整性与及时性 | 编码后的记录在被宣称可用时是否真的可用 |
| 政策范围内的临床文书完整性 | 记录是否足以支撑对这次就诊的辩护 |
| CPOE→结果闭环率 | 医嘱是否变成了结果，还是悬而未决 |
| EMPI 重复率与拆分周转时间 | 身份是否可信、是否可恢复 |
| 编码版本覆盖率（同时记录编码体系与版本的记录占比） | 术语腐坏是否可被发现 |
| 已签署文书的附录率 | 更正发生得有多频繁——该比例上升意味着上游存在可用性问题 |
| 临床/计费分歧率 | 两种真相在哪里不一致，以及是否已被解释 |
| 越权访问（break-glass）次数与复核 | 紧急访问是否属于例外，并且被复核 |

## 10. 支撑模型的公开材料

**已核验可访问（HTTP 200）：**

- **HL7 FHIR** — https://hl7.org/fhir/ — 临床数据模型。
- **DICOM 标准** — https://www.dicomstandard.org/ — 影像对象模型与边界。
- **WHO ICD** — https://icd.who.int/ — 诊断/操作编码（ICD-10、ICD-11）。
- **SNOMED International** — https://www.snomed.org/ — 临床术语（授权与国家版本
  尚待确认）。
- **openEHR** — https://www.openehr.org/ — 一种基于原型的、区别于 FHIR 原生
  存储的替代方案。
- **HAPI FHIR** — https://hapifhir.io/ · **dcm4che** — https://www.dcm4che.org/ —
  这两个模型族各自可引用的开源实现。

**中国法规依据（已引用；见 `regulatory-landscape.md`）：**

- **《网络数据安全管理条例》**（国务院令第790号，自2025-01-01 施行）——已取得
  全文。第二十二条要求对敏感个人信息（包括**医疗健康**）取得**单独同意**。
- **《医疗卫生机构网络安全管理办法》**（国卫规划发〔2022〕29号）。
- **《医疗卫生机构数据安全和个人信息保护管理办法（试行）》**
  （国卫规划发〔2026〕6号，五部门联合印发，2026-02-14 印发即施行）——当前
  行业专门数据规则。
- **《中华人民共和国网络安全法》**——**2025-10-28 修订，2026-01-01 生效**，
  条文序号已重新编排。任何条款级引用都必须使用 2026 年后的编号。

**提及但不主张：**

- **HIPAA**（美国）——清单引用了 HHS 页面；它对本环境的自动化探测没有响应，
  因此不做条款级映射。
- **LOINC**——对自动化探测返回 403；仅按名称引用。

> ⚠️ ASSUMPTION：本方案包按医院规模的部署建模。初级保健、公共卫生或兽医
> 规模的需求有实质差异，不在覆盖范围内。
