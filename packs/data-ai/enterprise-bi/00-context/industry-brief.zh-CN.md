# 00-context / 行业简报 — 企业 BI 与自助分析

## 1. 这套系统在价值链中的位置

一个组织的数据在被用来回答问题之前，一文不值。**BI 与自助分析平台**是问题
变成仪表盘、数字或决策的那一层。它位于数据平台（`lakehouse-platform` 是它的
兄弟方案包，不是它的主题）与每个需要知道点什么的人之间：

```
        数据平台（兄弟方案包）                  消费方
        ───────────────────────────                ─────────
        规范化模型 · 集市              高管（受管报表）
        契约 · 血缘 · 质量              分析师（临时探查）
        数仓与算力                      运营人员（嵌入式指标）
        │                               产品与研发团队
        ▼                              （嵌入式 / 数据应用）
  ┌────────────────────────────────────────────────────┐
  │  BI 与自助分析                                     │
  │                                                    │
  │  语义模型   ── RLS/CLS、经认证的指标                │
  │  语义层     ── 口径带版本且有归属                    │
  │  仪表盘/看板  ── 新鲜度与认证状态                    │
  │  自助分析    ── 已认证 vs. 用户内容                 │
  │  晋升        ── 用户 → 已认证的工作流               │
  └────────────────────────────────────────────────────┘
```

本方案包刻意**不是**数据平台。`AGENTS.md` 说：数仓内部留在兄弟方案包。剩下的
——也正是这里全部的主题——是**含义、权限与信任**附着到数据上的那一层。

## 2. 这个方案包真正关乎的那一件事

每一个持续到造成伤害的 BI 失败都是同一个形状：两个数字，标签相同，彼此矛盾。

那不是可视化问题，而是**定义**问题。所以本方案包的核心对象是**指标定义
（口径）**及其三个属性，按 `AGENTS.md`：

| 属性 | 含义 | 为何承重 |
|---|---|---|
| **带版本** | 一个指标定义有版本历史；旧制品仍固定在它们构建时所用的版本上 | 上季度报出的数字必须仍然可解释 |
| **有归属** | 每个指标都有一名具名负责人，默认不是一个团队 | 必须有人能够修改定义并对它负责 |
| **单一连接键** | 两个指标之所以可比，**是因为**它们按一个共享定义连接，而不是因为名字相同 | 这正是让「收入」在 40 个仪表盘上意味着同一件事的机制 |

> 没有连接键的语义层，只是给已经达成一致的人提供的一套共同词汇。连接键才是
> 他们真正达成一致的机制。无法连接的指标就是两个指标，无论它们叫什么。

## 3. 权限属于语义层

`AGENTS.md` 把 **RLS/CLS 规则放在语义模型内部**，而不是放在仪表盘配置里。

这个区分有具体后果：

| RLS/CLS 定义在…… | 后果 |
|---|---|
| **仪表盘** | 每个新图表都重新实现（而且通常实现不完整）同一条规则；同一数据的新消费方会静默绕过它；规则无法被单独测试 |
| **语义模型** | 规则只被求值一次，对每个消费方都在身份上下文存在的那一层求值；它可以作为单元被测试、作为定义被审计 |

行级安全（用户可以看到哪些行）与列级安全（哪些字段）*都是*语义层的关注点，
因为两者都是**身份 + 数据主体**的函数，而不是呈现方式的函数。

> ⚠️ ASSUMPTION: 本方案包假设平台能把用户身份与属性（组、区域、权限）提供
> 到查询上下文中，并认为这是平台要求而非企业目录的附加功能。无法把身份上下文
> 向下传递的部署根本无法执行语义层 RLS，并且必须明说这一点。

## 4. 新鲜度与认证是制品的属性

`AGENTS.md` 要求新鲜度与认证在**每一件制品上可见**——每个仪表盘、每个图表、
每条保存的查询。

这是一条设计陈述，不是界面偏好。一个新鲜度与认证被隐藏的数字，与可信的数字
无法区分，而认证的全部意义就在于被*看见*。

因此认证状态需要满足：

- **按制品**，而不是按许可证：已认证看板里的一张未认证图表就是一张未认证
  图表；
- **计算得出**，而不是手工标注：从底层模型的契约与流水线状态派生，因此不会
  与现实漂移；
- **无需交互即可见**：用户不该需要点一下才能知道该不该信任这个数字。

## 5. 自助分析把已认证与用户内容分开

`AGENTS.md` 要求自助分析区分**已认证**与**用户**内容，并在两者之间有一条
**晋升工作流**。

```
  用户探查 ──▶ 保存的查询 ──▶ 分享给某个组 ──▶ 提交评审
                                                        │
  已认证 ◀── 发布、附带新鲜度与负责人 ◀──────────────────┘
```

这个划分存在，是因为替代方案——一个无差别的仪表盘池——以一种可预测的方式
失败：制品数量增长、已认证占比下降，平台变成一个「找数字」的地方，而不是
「找到*那个*数字」的地方。

晋升是让这个划分富有成效而非仅仅具有限制性的机制：用户构建的制品不是一个
永久的二等对象，它是一个候选。

> ⚠️ ASSUMPTION: 本方案包假设晋升是**带评审的工作流**，而不是自动的。触发
> 条件（使用度、存续时间、负责人请求）以及它要求什么属于 L2 决策；本方案包
> 只固定这条边界存在，且跨越它是有意为之。

## 6. 核心流程（L1 视角）

1. **建模** —— 编写一个语义模型：数据集、实体、指标定义与 RLS/CLS 规则。
2. **发布** —— 模型被版本化；制品固定到一个版本。
3. **构建** —— 针对某个模型版本编写一个已认证仪表盘。
4. **探查** —— 分析师探查、构建查询、把它保存为用户内容。
5. **分享** —— 用户内容在其受众范围内分享。
6. **晋升** —— 用户内容被提交、被评审，或发布为已认证，或被带理由地拒绝。
7. **消费** —— 查看者打开一件制品，看到其认证状态与新鲜度，并在自己的
   RLS/CLS 下查询它。
8. **变更** —— 指标定义被修订并留下版本历史；制品标注自己使用的是哪个版本。
9. **审计** —— 谁在什么规则下访问了哪件制品，得到了什么结果。

## 7. 为什么这套系统格外难做对

- **定义比代码漂移得更快。** 一次会议里改变的指标含义，除非定义带版本，否则
  不会出现在任何 diff 中。
- **权限逻辑绝不能被复制。** 每一次 RLS 规则的重新实现都是一次独立的机会把
  它做错，而这种错误在有人去看错行之前都是不可见的。
- **自助分析与信任相冲突。** 同一个平台既要鼓励探查又要保证可靠性；除非
  已认证/用户的边界是明确的，这两股力量方向相反。
- **新鲜度是语义事实，不是运维事实。** 仪表盘「新鲜」是相对于底层模型上的一
  条*契约*，而不是相对于数据库上次写入的时间——而两者恰好在要紧的时候
  分道扬镳。
- **制品图谱的增长快过任何人的维护能力。** 一个建立在已废弃模型版本上的旧
  仪表盘不是错误；它是一个无人拥有的制品，而且它会被信任。

## 8. 定义质量指标

L1 框定意图；阈值在 L2 成为 NFR 目标。

| 指标 | 它回答什么 |
|---|---|
| 指标定义复用率（被一件以上制品使用的指标占比） | 语义层是共享的还是复制粘贴的 |
| 重复定义数量（同名不同语义） | 连接键是否真实存在 |
| 认证覆盖率（针对已认证模型的制品占比） | 信任是否是默认状态 |
| RLS/CLS 覆盖率（带语义层规则的数据集占比） | 权限是否集中 |
| 打开时的查询新鲜度（p50/p95） | 制品是否符合其契约 |
| 晋升周期时间（提交 → 发布） | 自助分析是否是一条有产出的路径 |
| 制品陈旧度（建立在被取代模型版本上的制品占比） | 图谱是否被维护 |
| 自助分析成功率（查询返回 vs. 报错/为空） | 探查是否可行 |
