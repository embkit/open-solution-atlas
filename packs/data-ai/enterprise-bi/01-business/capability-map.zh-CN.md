## 1. 一级能力

| # | 能力 | 它必须回答什么 | 说明 / L1 立场 |
|---|---|---|---|
| **CAP-01** | **语义模型** | 什么与什么相连，依循哪个键 | **连接键**是两个指标之所以可比的全部机制（`AGENTS.md`） |
| **CAP-02** | **指标定义（口径）** | 一个数字*意味着*什么，谁拥有它，这件制品用的是哪个版本 | 带版本 + 有归属（`AGENTS.md`）；本方案包的核心对象 |
| **CAP-03** | **访问控制（RLS/CLS）** | 给定用户可以看到哪些行与哪些列 | **在语义模型里，而不是仪表盘配置里**（`AGENTS.md`） |
| **CAP-04** | **编写与探查** | 一个问题如何变成一条保存的查询 | 自助分析的原材料 |
| **CAP-05** | **已认证制品** | 什么是可信的，用户是否知道 | 固定到一个模型版本；认证无需交互即可见 |
| **CAP-06** | **自助分析与晋升** | 用户内容如何成为已认证 | 已认证/用户的划分**带有**晋升路径（`AGENTS.md`） |
| **CAP-07** | **服务、嵌入与分发** | 指标如何到达人和产品 | 嵌入必须受同样的 RLS/CLS 约束，不是绕过路径 |
| **CAP-08** | **新鲜度与认证的计算** | 一件制品何时是最新的，以及它是**针对什么**计算出来的 | 从模型契约派生，绝不手工标注 |
| **CAP-09** | **治理、审计与生命周期** | 存在什么，什么是陈旧的，谁看过什么 | 对「这个旧仪表盘为什么这么说？」的回答 |
| **CAP-10** | **平台运维与成本** | 平台是否可运行、可负担 | 容量、调度、物化、归集 |

## 2. 边界（每项能力*不*拥有什么）

| 能力 | 明确**不**是它的职责 |
|---|---|
| 01 语义模型 | 数仓的物理存储——那是兄弟方案包 `lakehouse-platform` |
| 02 指标定义 | 决定一个数字是否*好*——由负责人决定；02 记录这个决定 |
| 03 访问控制 | 对用户做认证——那是 IdP；03 消费身份上下文 |
| 04 编写 | 授予权限——探查受 03 约束，绝不是例外 |
| 05 已认证制品 | 手工标注自己的信任状态——08 计算它 |
| 06 晋升 | 评审者的判断——06 承载工作流，而不是结论 |
| 07 服务与嵌入 | 重新实现权限——嵌入是**消费方**，03 同样适用 |
| 08 新鲜度 | 定义契约——那是模型负责人 / 02 |
| 09 治理 | 代替他人删除制品——它标记，负责人行动 |
| 10 运维 | 修改指标定义——运营者对口径没有权威 |

> 两条边界承载着本方案包的重量。**03**：权限逻辑绝不能被复制，因为每一次
> 重新实现都是一次独立的机会把它做错，而这种错误是隐形的。而 **07**：一个
> 绕过语义层的嵌入会把整套访问控制设计变成装饰。两者都可以在评审中检查。

## 3. 一级优先级

为讨论而完整，为估算而不完整；刻意不谈相对难度。

> ⚠️ ASSUMPTION: 能力 **02（口径）** 与 **03（RLS/CLS）** 被排在前面，是因为
> `AGENTS.md` 把单一连接键与语义层权限定为本方案包的两条不可谈判项。这是编辑
> 排序，不是以证据为依据的关键性论断。

## 4. 整个平台范围之外

- **数仓内部** —— 接入、存储、表格式、转换机制留在 `lakehouse-platform`
  （`AGENTS.md`）。
- **数据科学 / ML** —— 是集市的消费方，不是这里的主题。
- **制品图谱自身的报表** —— 本平台自己的使用分析也是受治理的内容，和其他
> 一切一样构建在语义层上。
- **许可与采购** —— 平台运维仅在其可运行范围内涉及。
- **某个具体产品或查询引擎** —— `stack_stance: stack-agnostic`。
