# ADR-0001 — 指标定义是本方案包的核心对象，而连接键是它的机制

- 状态：已接受
- 日期：2026-10-12
- 决策人：本方案包维护者

## 背景

`AGENTS.md` 陈述：指标定义（口径）带版本、有归属，并且是跨制品的唯一连接键。

每一个持续到造成伤害的 BI 失败都是同一个形状：两个数字，标签相同，彼此矛盾。
那不是可视化问题，而是**定义**问题。所以本方案包的核心对象是指标定义，而它的
三个属性不是建模惯例。

第三个属性才是让本方案包运转的那个，它值得展开：**连接键是两个指标之所以可比
的全部机制。** 没有连接键的语义层，只是给已经达成一致的人提供的一套共同词汇
——换句话说，它对产生它的那场分歧毫无作用。

## 备选方案

1. **以名字为契约** —— 两个同名指标就是同一个指标。便宜，而这恰恰是两个不同
   数字最终被贴上同一个标签的方式。
2. **有文档的定义，但没有声明的键** —— 定义存在且写得很好，可比性被留给写查询
   的人。分歧在文档中存活下来。
3. **带负责人、版本与已声明连接键的定义** —— 两个指标之所以可比，是因为它们
   按一个已声明的键相连；而同名不同语义的一对是一个**可检测的缺陷**。

## 决策

方案 3，由 BR-01、BR-02、FR-001、FR-002、FR-003、FR-004 以及 NFR-001、
NFR-002 强制执行。

负责人是一个**具名的人**，默认不是一个团队。在会议中变更的定义，除非有人对它
负责，否则永远不会出现在 diff 里。

## 后果

- 正面：「这两个仪表盘为什么对不上？」由它们的连接键与定义版本回答，而不是靠
  一次调查。
- 正面：重复定义变得可检测（NFR-002），而不是各说各话。
- 正面：对定义的变更是一个带版本、带具名负责人、带影响报告的动作，这正是让
  语义层成为一套共享系统而非一种共享约定的关键。
- 负面：负责人是一个人，所以团队重组可能让一个定义失去归属。本方案包要求
  有负责人，但未解决有人离职时会怎样。
- 负面：每一对指标都必须声明连接键，这是一份实打实的前期建模工作。NFR-001
  度量定义复用率，因为复用率低意味着这份工作被跳过了，而那一层不过是一堆
  复制粘贴。
