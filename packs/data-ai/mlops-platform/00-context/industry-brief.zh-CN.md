# 00-context / 行业简报 — MLOps 与模型生命周期平台

## 1. 本系统在价值链中的位置

机器学习模型不是程序。它是一个**经学习得到的制品**，其行为取决于已经不再以学习时形态存在的数据、已经继续演进的代码，以及自那以后已经发生变化的世界。

**MLOps 与模型生命周期平台**的存在，是为了让该制品**可复现、可晋级、可解释**。它是数据平台与生产决策之间的那一层：

```
   数据平台                     生产环境
   ─────────────                     ──────────
   特征源 · 数据仓库                  调用模型的应用
   传统系统 + 流式处理                决策引擎
   标签                              人在回路中
          │                                ▲
          ▼                                │
  ┌────────────────────────────────────────┴───────────────────┐
  │  MLOps 平台                                               │
  │                                                           │
  │  实验跟踪 ── 双重版本管理（代码 · 数据 · 特征）             │
  │  特征存储 ── 时间点正确性                                 │
  │  模型注册中心 ── 通往生产的唯一准入门禁 + 审批记录         │
  │  服务 ── 灰度发布 · 影子发布 · 回滚到某个版本              │
  │  监控 ── 对线上流量进行漂移检测，可审计                    │
  │  血缘 ── “为何会有这一预测”，端到端                       │
  │  治理 ── NIST AI RMF / ISO 42001 框架，绝不临时制定        │
  └────────────────────────────────────────────────────────────┘
```

核心难题**不在于**部署。生产模型是一个**复合制品**；除非平台在训练时已为此提供支持，否则事后无法重建其输入。

## 2. 双重版本管理：复合制品

`AGENTS.md` 规定了本方案包的第一法则：每个投入服务的模型版本都固定到一个由代码提交、数据快照和特征定义构成的**不可变组合**——并且该版本绑定是**可查询的**。

模型不只是版本 1.7。它是：

| 组件 | 为何必须固定 |
|---|---|
| **代码提交** | 生成权重的训练代码 |
| **数据快照** | 精确的训练数据，而不是明天重新求值会得到不同结果的查询 |
| **特征定义** | 将数据转换为特征的转换代码及时间点语义 |

版本绑定**可查询**才是真正起作用的属性。版本编号本身只是一个指针；平台必须能够回答“模型 1.7 究竟学自什么数据，又使用了什么代码？”——而且无需进行考古式排查。

> 这与 `telecom-bss` 的不可变计费事件、`omnichannel-commerce` 的定价快照以及 `growth-analytics` 的版本化事件模式遵循同样的纪律：**编号必须能够在事后复现**，否则所有争议都无从裁决。在机器学习中，后果更为严峻——无法复现的模型无法重新训练、审计或为其辩护。

> ⚠️ ASSUMPTION: “代码提交、数据快照和特征定义”是本方案包依据 `AGENTS.md` 确定的三元组。实际部署通常还会固定更多内容（超参数、框架版本、随机种子、环境）。本方案包并不主张这三者已经足够——只主张它们共同构成最小版本绑定。

## 3. 特征偏斜是正确性问题，而非日常维护问题

`AGENTS.md` 将**训练服务偏斜**视为首要的正确性问题。

偏斜是一种静默故障：模型训练时使用的特征按一种方式计算，而服务时提供的特征却按另一种方式计算——窗口不同、连接不同，缺失值采用不同的默认值。模型能够运行，返回看似合理的数字，但结果是错的。不会发生崩溃；只会让预测性能下降。

时间点正确性正是防止这种情况的机制。特征值以**观察时点**为基准定义，并且只使用当时可用的数据：

- “7 天消费”特征不得包含标签形成之后的消费；
- 一次补算必须复现模型训练时看到的值，而不是事后视角所允许的值；
- 同一套定义必须在训练、补算和服务中以完全相同的方式运行。

> 特征存储正是为此而存在，而非为了缓存。不强制执行时间点语义的存储，就是缓存加治理文档（反模式）。

## 4. 模型注册中心是唯一门禁

`AGENTS.md`：模型注册中心是通往生产环境的**唯一准入门禁**，并配有**明确的审批记录**。

两项属性：

- **单一门禁**——生产环境中的服务仅从模型注册中心读取模型。任何其他方式进入生产环境的模型（通过笔记本、部署脚本、开发人员的笔记本电脑）都是未注册制品，其版本绑定无法查询；“线上运行的是哪个模型？没人知道”正是由此导致的最常见单一原因。
- **明确审批记录**——晋级是具名主体基于明确依据实施并记录在案的行为，而不是某个恰好通过的 CI 作业。

> 审批记录使后续审计成为可能：“谁授权了这个模型、依据什么证据、在哪一天”必须能够从模型注册中心得到回答，而且答案不应存在于其他任何地方。

## 5. 服务：回滚是一项版本操作

由于模型是由各项固定内容构成的复合制品，**回滚就是选择较旧的版本绑定**。这正是双重版本管理不只是记账工作的原因：没有双重版本管理，回滚并非只是困难，而是根本不可能。

因此，服务必须支持使模型能够安全变更的操作：**灰度发布和影子发布**（将一部分流量路由至新版本；只计算但不提供服务），以及**即时回滚到已固定版本**。

## 6. 血缘必须回答“为何会有这一预测”

`AGENTS.md` 要求血缘端到端回答**“为何会有这一预测”**。

对于单次预测，这意味着：使用的是哪个模型版本、哪些特征值、来自哪些上游数据、处于什么时间、采用了哪种转换。不是一张图——而是一个能够得到答案的查询。

```
   预测  ──▶ 模型版本（代码 · 数据 · 特征版本绑定）
             └─▶ 使用的特征值
                 └─▶ 上游数据行及其来源性质
                     └─▶ 源系统，以及对应时间
```

> 任何低于此的内容都只是血缘图（反模式），它只能向工程师解释架构，对审计人员却毫无价值。

## 7. 漂移检测在线上流量上运行

`AGENTS.md`：漂移检测在**线上流量**上运行，且其**结果可审计**。

两项属性：实时（而不是在离线留出集上运行；这些集合会悄然变得不再像生产环境），以及可审计（以便日后能够为依据漂移证据作出的决策进行辩护）。

该机制还必须区分究竟发生了哪种漂移：

| 类型 | 含义 |
|---|---|
| **数据漂移/协变量偏移** | 输入分布发生了变化 |
| **概念漂移** | 输入与输出之间的关系发生了变化 |
| **预测漂移** | 输出分布发生了变化——即使没有标签也能察觉 |
| **标签漂移/泄漏** | 标签相对于其应有取值发生了变化，或标签发生了泄漏 |

将这些现象混为一谈，只会得到一个不断触发告警却不解释任何问题的仪表板。

## 8. 治理具有明确框架

`AGENTS.md`：治理遵循 **NIST AI RMF** 和 **ISO/IEC 42001**——风险管理与文档编制——**绝不采用临时政策**。

> 本方案包的立场是，两者均作为**治理框架（采用为形状）**（风险界定加文档制品）被采用，而非作为符合性声明。这与 `telecom-bss` 采用 ODA/Open API 词汇的立场相同：采用词汇，而非声称符合标准。

实际后果是，治理由一组**责任归属明确的制品**构成：模型卡、用途声明、局限说明、评估结果、审批记录，以及这些制品所属的风险界定。每项制品在模型注册中心或监控轨迹中都有归属位置；正是这一点将治理与 wiki 页面区分开来。

> 根据本仓库的范围决定，**未验证任何一个框架的任何条款**。它们在 `manifest.yaml` 中仅作为名称标识列出，本方案包只说明由此产生的设计后果。

## 9. 核心流程（L1 视图）

1. **实验**——将一次运行连同代码提交、数据快照和特征定义作为一个整体进行跟踪。
2. **评估**——根据声明的指标评估该运行，并按细分维度进行分片评估，而不只是总体评估。
3. **注册**——注册该制品及其版本绑定。
4. **审批**——具名主体基于记录在案的依据进行审批。
5. **服务**——先灰度发布，再全面发布；影子发布可用于离线评估。
6. **监控**——对线上流量进行漂移检测，并保留可审计结果。
7. **响应**——回滚到已固定版本，或在新的版本绑定下重新训练。
8. **解释**——对于任意预测，沿血缘追溯至来源。

## 10. 为什么这个系统格外难以正确实现

- **可复现性必须被设计进去。** 无法事后添加，因为等到有人提出问题时，生成模型的数据和特征定义已经消失。
- **静默劣化是常态故障模式。** 什么都不会抛出异常；只是数值逐渐变差，而且除非漂移监控发挥作用，否则不会触发告警。
- **回滚要求旧版本绑定仍然存在。** 对数据快照和特征定义的保留是服务要求，而不是归档策略。
- **治理与吞吐量相冲突。** 模型注册中心添加的每项控制措施都会成为通往生产环境路径上的摩擦点；临时政策之所以出现，恰恰是因为受控路径更慢。
- **风险很少在评估环节暴露。** 总体指标会掩盖细分群体故障；真正重要的审计存在于无人查看的分片中。
- **时间点正确性既昂贵又不直观。** 每次走捷径都会导致 §3 中描述的静默故障。

## 11. 质量指标定义

L1 用于界定意图；阈值在 L2 阶段成为 NFR 目标。

| 指标 | 回答的问题 |
|---|---|
| 版本绑定完整度（具备可查询的代码/数据/特征固定项的已服务模型占比） | 制品是复合的还是黑盒 |
| 时间点正确性违规（训练与回放对比） | 是否存在偏斜 |
| 注册中心门禁覆盖率（拥有审批记录的生产模型占比） | 门禁是否真实存在 |
| 回滚到已固定版本所需时间 | 回滚是否根本可行 |
| 漂移检测覆盖率（设有监控器的特征占比） | 劣化是否可见 |
| 从检测到漂移到采取措施所需的时间 | 监控是否改变行为 |
| 血缘可查询性（预测 → 来源） | “为何会有这一预测”是否有答案 |
| 生产模型的模型卡完整度 | 治理是否以制品为基础 |
