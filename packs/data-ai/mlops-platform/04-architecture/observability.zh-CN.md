## 永不取舍的五项不变量

`serving_without_binding`、`serving_without_registry`、`serving_without_approval`、
`feature_replay_mismatch` 和 `unregistered_promotion_attempt` 必须为 **零**。

任何一项都不以吞吐量或延迟为交换条件。每项都实行零容忍，因为在此领域，放宽其中任何一项都不会使某个数值下降——而会使平台的主张**无法验证**，后果更为严重：模型仍会继续提供服务，指标看起来仍然一切正常，而日后审计所需的证据根本不存在。

> 一个所有信号都显得无差别的仪表盘，会训练团队把所有信号都拿来权衡。
> 将这五项明确标示出来，就能让这种取舍变得明确且可审查。

## 平台必须能够回答的问题

| 问题 | 回答来源 |
|---|---|
| “这个版本从什么数据中学习，使用了什么代码？” | 经查询的版本绑定 |
| “谁依据什么证据授权了这个模型？” | 审批记录 |
| “它对每个已声明的分片是否都正确？” | 分片评估 |
| “为何会有这一预测？” | 预测追溯 |
| “是否在线上流量上检测到性能退化，以及采取了什么措施？” | 漂移发现及其响应 |
| “当前线上运行的是哪个版本？” | 模型注册中心——因为不存在其他路径（BR-05） |

> 每个问题都可以**依据平台自身的记录**作答，而无须通过事后重建。
> “当前线上运行的是哪个版本”是实践中最常失效的问题，而它之所以失效，恰恰是因为曾存在第二条生产路径。

## 追溯与关联

- 一条**训练**追溯贯穿：版本绑定 → 训练作业 → 评估 → 分片 → 注册。每个步骤都携带版本绑定，因此模型的派生过程始终可以明确归因。
- 一条**服务**追溯贯穿：读取模型注册中心 → 部署 → 流量拆分 → 回滚事件。每个步骤都携带模型版本，因此“当前由哪个版本绑定提供服务”是一个可查询问题，而不是运维猜测。
- 一条**解释**追溯贯穿：预测 → 特征值（附带定义版本）→ 上游数据行 → 源系统。每个步骤都携带追溯 ID。

## 告警策略

- **呼叫（Page）**：任何不变量违规，以及漂移发现超过 NFR-007 规定的响应时限且尚无响应时，均应呼叫。
- **工单（Ticket）**：针对分片覆盖缺口、漂移监控缺口、版本绑定保留期缺口和回滚时间未达标，应创建工单。
- **审查（Review）**：每周审查晋级周期时长（NFR-012）：趋势上升意味着受控路径已变得比不受控路径更慢——这恰恰是未注册生产路径重新出现的条件，也是能够最早识别准入门禁失效的信号。
