## 1. 一级能力

| # | 能力 | 必须回答的问题 | 备注 / L1 定位 |
|---|---|---|---|
| **CAP-01** | **实验跟踪** | 究竟是什么产生了这一结果 | 版本绑定 **作为一个整体** 记录，而非以松散元数据形式记录 |
| **CAP-02** | **特征存储** | 服务看到的是否与训练一致 | 时间点正确性是其存在理由；否则就是缓存加治理文档（反模式） |
| **CAP-03** | **训练与补算** | 能否重建 | 回放必须复现训练时的特征值 |
| **CAP-04** | **模型注册中心** | 能否进入生产环境 | **唯一准入门禁**，包含审批记录、风险等级和生命周期状态 |
| **CAP-05** | **服务与发布** | 线上运行的是什么，能否回退 | 灰度发布、影子发布以及回滚到较早的版本绑定——之所以可行，仅因为版本绑定存在 |
| **CAP-06** | **监控与漂移** | 在线上流量中是否仍然正确 | 在线运行，而非离线；**可审计**结果 |
| **CAP-07** | **血缘与可解释性** | 为何会作出该预测 | 提供答案的查询，而非图表 |
| **CAP-08** | **治理制品** | 此模型用于什么，有哪些局限 | 模型卡、用途声明、局限、评估、下线退役——每项都有明确归属 |
| **CAP-09** | **评估与分片指标** | 对*所有人*是否都正确 | 总体指标会掩盖分片故障；审计对象是无人查看的分片 |
| **CAP-10** | **平台运维与安全** | 谁可以晋级，谁可以提供服务 | 晋级权与服务权相互分离 |

## 2. 边界（各项能力*不*负责什么）

| 能力 | 明确**不**归其负责的事项 |
|---|---|
| 01 实验跟踪 | 判断模型是否良好——评估由 09 负责 |
| 02 特征存储 | 定义业务含义——由特征负责人定义；02 强制执行时间点语义 |
| 03 训练 | 决定使用什么进行训练——由研究人员决定；03 使其可复现 |
| 04 模型注册中心 | 审批模型——由具名主体审批；04 负责**记录** |
| 05 服务 | 选择模型版本——生产环境只读取模型注册中心 |
| 06 监控 | 决定响应措施——它负责检测并提供证据；由人员/流程响应 |
| 07 血缘 | 论证预测的合理性——它提供（“是什么”）链条；合理性论证由制品提供 |
| 08 治理制品 | 制定政策——这些制品落实所采用的治理框架形态 |
| 09 评估 | 部署通过评估的模型——04 是进入生产环境的闸门 |
| 10 运维 | 晋级模型——访问权限与晋级权分离 |

> 有三项边界支撑着本方案包。**02**：不强制执行时间点语义的特征存储只是一个带文档的缓存层。**04**：
> 生产环境必须从模型注册中心读取，因为以其他任何方式进入生产环境的模型，其版本绑定无法查询。此外，
> **04 与 10**：服务运维人员与审批人是不同的权责主体；否则，事件响应就会变成未经复核的晋级。

## 4. 整个平台的范围外事项

- **数据平台** — `lakehouse-platform`；本方案包通过契约使用特征和标签。
- **模型指标上的 BI 界面** — `enterprise-bi`。
- **模型架构研究** — 平台负责跟踪和设闸；不负责创造模型。
- **调用模型的应用逻辑** — 属于影响范围，而非本方案包的对象。
- **特定的 ML 框架、存储实现或服务技术栈** — `stack_stance: stack-agnostic`。
