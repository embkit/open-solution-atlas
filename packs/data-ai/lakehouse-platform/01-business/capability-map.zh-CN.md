## 1. 一级能力

| # | 能力 | 它必须回答什么 | 说明 / L1 立场 |
|---|---|---|---|
| **CAP-01** | **接入** | 数据如何落地，以及被重新投递时会发生什么 | 幂等落地与重放是正确性要求，而不是重试 |
| **CAP-02** | **存储与表格式** | 数据如何被存储，使重处理成为可能 | 原始不可变；表格式是带标准的 L2 决策 |
| **CAP-03** | **转换与建模** | 原始如何可验证地变成业务形态 | 层间的契约就是架构（`AGENTS.md`） |
| **CAP-04** | **数据质量** | 数据是否可用，以及不可用时会发生什么 | 阻断与告警闸门是**不同的机制**（`AGENTS.md`） |
| **CAP-05** | **目录与元数据** | 存在什么、谁拥有它、如何分类 | 治理与发现的基础底座 |
| **CAP-06** | **血缘与影响分析** | 一个数字从哪来，一次变更会破坏什么 | 字段级，源字段 → 集市列（`AGENTS.md`） |
| **CAP-07** | **访问控制与隐私** | 谁可以读什么，以及删除如何被强制 | 平台强制；擦除是一条流水线（`AGENTS.md`） |
| **CAP-08** | **编排与可运维性** | 工作如何被调度与安全重跑 | 分区重处理必须是一等能力 |
| **CAP-09** | **提供与消费** | 消费方如何读取而不绕过控制 | 强制执行点，而不是把问题挪到别处 |
| **CAP-10** | **成本与容量管理** | 平台是否可持续 | 一项正确性关切，因为负担不起的重算会被跳过 |

## 2. 边界（每项能力*不*拥有什么）

| 能力 | 明确**不**是它的职责 |
|---|---|
| 01 接入 | 更正源数据语义——那是 03 |
| 02 存储 | 业务校验——那是 04 |
| 03 转换 | 决定数据的含义——那是 05（管家） |
| 04 数据质量 | 决定一次失败是否可接受——那是管家，不是闸门 |
| 05 目录 | 强制访问——它*描述*分类；07 强制它 |
| 06 血缘 | 做决定——它回答「什么会坏」，由负责人决定 |
| 07 访问与隐私 | 拥有留存策略——那是治理（见 `regulatory-landscape.md` 第 4 节） |
| 08 编排 | 业务逻辑——它运行作业，不决定转换 |
| 09 提供 | 重新实现访问控制——它绝不能成为第二个强制执行点 |
| 10 成本 | 限制正确性工作——成本提供信息，不是否决 |

## 3. 一级优先级

这张地图为讨论而完整，为估算而不完整。本方案包刻意不谈相对难度——那需要一个
参考部署。

> ⚠️ ASSUMPTION: 能力 **03（层间契约）** 与 **06（字段级血缘）** 被排在
> 前面，是因为本方案包的 `AGENTS.md` 把它们视为架构级而非功能级。这是编辑
> 排序，不是以证据为依据的关键性论断。

## 4. 整个平台范围之外

- 源系统的业务逻辑；平台消费它们，不拥有它们。
- 本组织数据治理**政策**的定义——平台执行决定，治理委员会做出决定。
- 某个具体表格式、引擎或云的选择——`stack_stance: stack-agnostic`；此类
  选择属于带标准的 `variants/` 覆盖层。
- 实时服务/OLAP 产品的内部实现——本方案包覆盖平台必须向消费方提供什么，而不
  是查询引擎如何被构建。
