# 00-context / 行业简报 — 企业数据仓库与湖仓平台

## 1. 这套系统在价值链中的位置

一个企业在几十个系统里积累数据，而这些系统从设计上就彼此不一致。**数据平台**
是把这堆数据变成可回答问题的那个横向系统：它接入、整合、策展并提供数据，使
报表、分析与机器学习描述的是*同一个*版本的真相。

它位于每一个生产系统与每一个消费系统之间，而它的全部价值在于：两侧都不必
知道对方的存在。

```
   源系统                        消费方
   -------------                  ---------
   OLTP 数据库 / ERP / CRM        BI 与仪表盘
   应用日志 / 事件                数据科学 / ML
   SaaS 与伙伴数据源               运营应用
   IoT / OT 遥测                  监管与法定报送
   文件 / 对象存储                 数据产品与 API
            │                            ▲
            ▼                            │
   ┌────────────────────────────────────────┴─────────────────────┐
   │  数据平台                                                   │
   │                                                              │
   │  接入 ──▶ 存储（原始、不可变）──▶ 规范化 ──▶ 提供            │
   │             │                        │                      │
   │             └── 目录与元数据 ◀───────┘                      │
   │             └── 质量闸门 ── 血缘 ── 访问控制                  │
   └──────────────────────────────────────────────────────────────┘
```

本方案包把平台建模为**一条流水线加一层契约**，而不是一个产品：各层与其间
的契约就是架构（`AGENTS.md`）。

## 2. 本方案包视为架构的分层

| 层 | 内容 | 可变性 |
|---|---|---|
| **原始 / bronze** | 落地即存的源数据，每个来源一种记录类型 | **不可变、仅追加** —— 绝不编辑 |
| **规范化 / silver** | 去重、类型化、已校验、按规范键连接 | 可重处理；由重处理更正，绝不由 UPDATE 更正 |
| **集市 / gold** | 面向特定消费的业务形态聚合 | 由规范化派生；可丢弃、可重建 |

> 分层是一份**契约**，不是一套文件夹方案。原始不可变，因此任何下游结果都总能
> 从头重算；规范化是源头特有的混乱只被解决一次、且为所有人解决的地方。一个
> 允许集市读原始、或允许就地编辑的平台，已经破坏了使重处理成为可能的性质。

## 3. 核心张力：存储已与算力解耦

这个类别是被那些把事务型表抽象**放在廉价对象存储之上**的开放表格式重塑的：

| 格式 | 项目 | 值得注意的设计重点 |
|---|---|---|
| **Apache Iceberg** | Apache Iceberg（https://iceberg.apache.org/） | 带隐藏分区与分区演进的开放表格式 |
| **Delta Lake** | Delta Lake（https://delta.io/） | 对象存储上的事务日志与乐观并发 |
| **Apache Hudi** | Apache Hudi（https://hudi.apache.org/） | 记录级 upsert 与增量处理 |

> ⚠️ ASSUMPTION: 本方案包点名这三种，是因为它们是被广泛采用的开放表格式，
> **而不是**因为本方案包比较过它们。格式选择是一项架构决策，属于 L2/L3 带
> 实际标准的 `variants/` 覆盖层——本方案包保持中立，这正是
> `stack_stance: stack-agnostic` 所承诺的。

无论格式如何选择，平台都必须处理的后果：

- **时间旅行与快照** —— 每次读取都看到一致的快照；重处理是「读快照、写新
  快照」，而不是「改写行」。
- **schema 演进** —— 新增、改名与删除列绝不能破坏既有读取方。
- **小文件与压实压力** —— 流式写入会产生许多小文件；压实是一项与正确性相邻
  的定时作业，而不是例行杂务。
- **分区重处理** —— 「重载上周二」必须是一等的安全操作（`AGENTS.md`）。

## 4. 核心流程（L1 视角）

1. **接入** —— 从来源拉取/推送到原始；批量、微批或流式；至少一次投递且落地
   幂等。
2. **剖析与校验** —— 在到达时度量质量；把违规路由到阻断或告警路径
   （`AGENTS.md`：两者是*不同的*）。
3. **规范化** —— 去重，标准化类型与键，解析缓慢变化引用。
4. **策展与建模** —— 按已声明的契约构建集市。
5. **提供** —— BI、ML 特征抽取、API、导出；在平台而不仅仅在 BI 工具中强制
   访问控制（`AGENTS.md`）。
6. **观测** —— 新鲜度、体量、质量、成本、血缘健康。
7. **治理** —— 分类、留存，以及*运行式*删除（`AGENTS.md`：GDPR/PIPL 擦除是
   一条流水线，不是一张工单）。

## 5. 为什么这套系统格外难做对

- **下游信任就是产品。** 一次静默的类型强制转换或迟到的重复，就会摧毁对建立
  在其上的每个数字的信心，而信心的恢复比失去慢得多。
- **「可重处理」是一项设计性质，不是一个功能。** 它要求不可变的原始、确定性的
  转换与稳定的分区键——三者都要在开始时决定，事后再补极其昂贵。
- **停在表层的血缘毫无用处。** 「哪个仪表盘数字错了？」只有下探到
  **源字段 → 集市列**级别的血缘才能回答（`AGENTS.md`），那是字段级图构建，
  而不是表级文档。
- **访问控制属于平台。** 只在 BI 层强制的分类，会被每一个其他消费方绕过
  （`AGENTS.md`）。
- **删除是一条运行流水线。** 一项法定擦除权，无法靠一份跨原始、规范化、
  集市、缓存、导出、日志与 ML 训练集的手工操作手册来满足。
- **成本是一个正确性关切。** 一次技术上正确而财务上毁灭性的重算会被跳过，
  这正是团队最终开始信任陈旧数据的方式。

## 6. 定义质量指标

L1 只框定意图；阈值在 L2 成为 NFR 目标。

| 指标 | 它回答什么 |
|---|---|
| 数据新鲜度（按契约） | 每个集市有多新，是否在契约之内 |
| 流水线成功率与 MTTR | 交付的可靠性与修复的速度 |
| 按数据集划分的质量闸门通过率 | 问题在上游生产方还是平台 |
| 完整分区的重处理时间 | 从逻辑缺陷中恢复是否有界 |
| 血缘覆盖率（已解析上游的字段占比） | 「这个数字为什么错」是否可被回答 |
| 访问控制覆盖率（已强制策略的分类数据集占比） | 治理是真实的还是仅是愿景 |
| 擦除 SLA（请求 → 已核验的移除） | 删除是否是一项运行能力 |
| 每次被服务查询 / 每个作业的成本 | 规模化是否可持续 |
