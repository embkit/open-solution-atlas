# 00-context / 行业简报 — 增长分析与实验

## 1. 这套系统在价值链中的位置

产品增长决策就是下注：做一个功能、发一次活动、改一个价格。**增长分析与实验
平台**是把这些下注变成度量的系统——事件跟踪、漏斗、留存、归因，以及最
重要的、**真正能证明点什么**的实验。

```
   产品 / 应用 / 网页                   决策消费方
   ───────────────────                  ──────────────────
   用户动作（事件）                     产品经理（漏斗、实验）
   会话 · 身份                         增长 / 市场（活动、人群）
   购买 · 试用                          数据科学（因果估计）
   活动 / 广告来源                      ┌──────────────────────────────┐
   │   ┌────────────────────────────▶│  增长分析                     │
   │   │   事件 Schema 注册表 ───▶│  事件 Schema 注册表 ── 主干   │
   │   └────▶ 身份解析            │  事件身份解析                   │
   │        ┌──▶ 漏斗 · 人群      │  数仓导出                        │
   │        └──▶ 归因             │  同意状态强制                    │
   └── 消息 / 广告目的地 ◀──┘  实验引擎                        │
```

它与企业 BI（兄弟方案包 `enterprise-bi`）有一个决定性的区别：BI 回答「正在
发生什么」，而增长分析必须回答**「是什么造成了它」**——这让严谨成为系统的
定义性属性，而不是一个报表细节。

## 2. 主干：事件 Schema 注册表

`AGENTS.md` 说得很直白：**未被治理的事件让每个数字都不可复现。**

一个事件只到达一次。没人能回头要求客户端用不同的属性名重新发一遍。所以，
当一个应用版本带着被改名的字段上线时，每一个建立在旧名字上的历史漏斗都会
静默地改变含义——没有部署、没有 diff、没有告警。

因此注册表就是主干，它做四件一页文档做不到的事：

| | |
|---|---|
| **声明** | 存在哪些事件与属性，它们的类型与含义 |
| **校验** | 在采集时校验传入事件——畸形事件被隔离，而不是被静默接受 |
| **版本化** | 属性改名是带映射历史的迁移，因此旧查询保持可解释 |
| **记录** | 每次 schema 变更都是一个带作者的版本化事件，因此漏斗的变更可被归因 |

> 一个没有注册表的增长平台，其*自身定义*的版本历史指向的是含义在它脚下已经
> 改变的数据。它上报的每个数字在严格意义上都不可复现：没人能重建它上个月
> 是什么意思。

## 3. 身份合并必须可逆且可删除

增长分析的经典模式是把一个用户跨设备、跨会话缝合成一个档案。`AGENTS.md` 让
这件事**可逆且可删除**。

两个彼此不同的属性，而两者都是设计要求：

- **可逆** —— 一次错误的身份合并（两个人被合并、一个人被拆开）必须能够撤销，
  而且撤销必须传播到派生事实（漏斗、人群、实验）。一个无法撤销的身份合并，
  就是关于某个人的一个谁也无法更正的决定。
- **可删除** —— 被合并的档案可以按请求被移除或切断，而嵌入该身份的派生数据
  不得让它复活。

> 第二点是这个模式通常崩坏的地方：档案被删了，但事件仍然携带合并所用的
> 匿名标识符，于是身份可以从残留中重新形成。不覆盖连接键的删除不是删除。

## 4. 同意在采集与激活两处被强制

`AGENTS.md` 要求同意状态在**两个**点上被强制。多数实现只做一个：

| 点 | 它控制什么 |
|---|---|
| **采集** | 一个事件是否被采集，以及在何种同意状态下 |
| **激活** | 已采集的数据是否被*用于*某个目的——发到活动、上传到广告网络、丰富一个档案 |

只在采集处强制会产生那个常见失败：多年前在宽泛同意状态下采集的数据，日后
被用于一个从未被同意过的目的。只在激活处强制会产生另一个失败：什么都照收
不误，于是屋子里的一个租客被拿来为另一个租客背书。

> 因此同意是数据的**有状态、按目的限定的属性**，在两个边界上都被检查，而不
> 是在注册时采集的一个布尔值。

## 5. 广告网络是目的地，不是所有者

`AGENTS.md`：广告网络与消息渠道是**抽象层之后的目的地**，绝不是数据的所有者。

这是一条架构陈述。平台拥有事件模型、身份模型与实验分配。某个网络的 SDK 是
通往一个拥有自己 schema 与自己语义的**目的地**的传输通道。允许目的地来定义
schema，意味着平台自己的数字被第三方的版本节奏挟持。

这个抽象层换来的是：无需一个项目就能换目的地、目的地宕机不会变成平台宕机，
以及无论某个网络回报什么，事件身份都保持一致。

## 6. 实验需要真正的统计

`AGENTS.md` 点名了要求：样本量、**SRM**（样本比例不匹配）、护栏、保留组
——「不是百分比比较」。

这是把增长平台与「带了个 A/B 开关的仪表盘」区分开的那部分：

| 机制 | 它防止什么 |
|---|---|
| **检验力 / 样本量** | 在噪声上宣布赢家——最常见也最昂贵的失败 |
| **SRM 检测** | 污染每一次比较的分配缺陷，而它看起来像一个*结果* |
| **护栏指标** | 为换取转化提升而牺牲健康指标（延迟、取消、退款） |
| **保留组** | 整个实验计划的漂移：这个平台还检测得出它以前检测得出的东西吗 |
| **偷看纪律** | 因为一个好看的中期结果而提前停止实验——数学上必然抬高假阳性 |
| **新奇 / 首因效应处理** | 把短期行为变化读成长期效应 |

> 一个不上这些东西就报告「变体 B 好 3.4%」的实验引擎，什么都没测出来。这
> 个数字可能没错却毫无意义——那比一个错误更糟，因为它会被信任。

## 7. 核心流程（L1 视角）

1. **埋点** —— 一个事件 schema 在任何客户端发出它之前，就在注册表中被声明并
   版本化。
2. **采集** —— 客户端发出一个事件；它按 schema 被校验；失败项被隔离并带
   理由。
3. **身份解析** —— 匿名标识符、设备、会话与已知用户被关联，合并被记录且可逆。
4. **分析** —— 漏斗、人群、留存与归因在解析后的身份图上计算。
5. **实验** —— 用户被随机分配且比例可核查；包括护栏在内的指标连同样本量、
   SRM 检查与保留组一起计算。
6. **激活** —— 一个分群经由抽象层在对应目的的同意状态下发往消息或广告
   目的地。
7. **导出** —— 精选事件与实验结果流向数仓。
8. **撤回** —— 同意被撤回；该目的的采集停止，激活立即停止。

## 8. 为什么这套系统格外难做对

- **数据只到达一次。** 对于一个被改错名字的属性，没有「重新摄入上个季度」
  这回事。schema 治理是唯一的防线，而它必须发生在客户端上线*之前*。
- **身份位于一切的上游。** 每一个漏斗、人群与转化都是「身份如何被解析」的
  函数，而一次合并错误会改变它们全部。
- **统计上的不负责任是廉价的。** 报告百分比差异很容易而且看起来严谨；正确
  地做需要样本量、SRM、护栏、保留组与偷看纪律——它们没有一项在输出中可见，
  而缺失时又全部不可见。
- **隐私与度量确实冲突。** 同意强制减少了可度量的总体；身份合并恰恰是造就
> 档案的那件事；两者必须共存，而谁也不能假装获胜。
- **目的地会写回自己的数字。** 把平台指标与广告网络的报表做交叉核对，是一项
> 反复出现却没人预留预算的对账工作。
- **严格意义上的回填是不可能的。** 一次 schema 修复会改变历史的含义；一次
  schema *迁移* 是最接近的东西，而它必须是显式的。

## 9. 定义质量指标

L1 框定意图；阈值在 L2 成为 NFR 目标。

| 指标 | 它回答什么 |
|---|---|
| schema 变更前置时间（在客户端首次发出之前声明） | 治理是被动的还是主动的 |
| 按来源/客户端版本统计的隔离事件率 | 埋点是否健康 |
| 身份合并/撤销的量与比例 | 合并是否可信、是否可更正 |
| 同意强制完整度（两个点） | 强制是否真实 |
| 实验速度 / SRM 失败率 | 分配是否可靠 |
| 实验检验力（实际 vs. 计划） | 实验能否做出任何决定 |
| 护栏违规率 | 指标是否被用来换转化 |
| 保留组差值（平台整体提升 vs. 保留组） | 实验计划是否仍然有效 |
| 目的地送达成功率与对账偏差 | 激活是否真的落地 |
