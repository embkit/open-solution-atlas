## 永不被交易的五条不变量

`undeclared_event_ingested`、`deletion_incomplete_join_keys`、`srm_unhandled`、
`activation_without_consent_check` 与 `collection_without_consent_check` 必须为
**零**。

其中两条——两项同意检查——是本方案包里仅有的失败关闭规则。一个未知的同意状态
被当作通用许可证，正是 BR-11 存在所要防止的失败，因此该边界失败关闭而不是
降级。

> 另外三条之所以零容忍，是因为每一条都让平台所作的某个论断
> **不可核验**而不只是错误：一个不可复现的数字、一次可以被击败的删除，以及一次
> 从未被度量的比较。

## 平台必须能够回答的问题

| 问题 | 由什么回答 |
|---|---|
| 「这个漏斗上个月为什么跌了？」 | 每个事件的 schema 版本，以及针对它记录的变更 |
| 「这个人真的被删除了吗？」 | 三段式删除记录——档案、连接键、派生事实 |
| 「我们是不是发给了从未同意的人？」 | 激活记录及其目的与同意依据 |
| 「这个实验是真的吗？」 | 引擎的分配记录、比例核查，以及预先声明的决策规则 |
| 「这次活动的成员资格在途中变了吗？」 | 快照的解析时间戳与活动周期对照 |
| 「我们的数字与广告网络的一致吗？」 | 对账比较，以平台的数字为基准 |

> 每一个都能从平台自己的记录中回答。第一个和第四个最常被用重建而不是用记录
> 来回答。

## 轨迹与关联

- 一条**接入**轨迹贯穿：客户端发出 → schema 解析 → 校验 → 接入或带理由隔离。
  每一步都携带 schema 版本，因此一次属性改名可归属于一个版本。
- 一条**激活**轨迹贯穿：分群快照 → 使用目的的同意检查 → 映射 → 发送。每一步
  都携带目的与同意依据，因此「这被允许了吗」无需推断即可回答。
- 一条**实验**轨迹贯穿：决策规则 → 分配 → 比例核查 → 主指标与护栏指标 → 在
  声明的时点读数。

## 告警策略

- **呼叫值班**：任一不变量被突破，以及护栏突破超过声明阈值。
- **开单**：无理由的隔离、无版本的导出、实时视图分群的检测，以及合并/撤销延迟。
- **每周复核**schema 变更前置时间（NFR-011）：「先声明后发出」的占比下降意味着
  埋点正在跑在治理前面，而不可复现数字的风险正在悄悄累积。
