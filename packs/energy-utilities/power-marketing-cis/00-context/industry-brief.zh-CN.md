# 00-context / 行业简报 — 电力营销与客户信息系统

## 1. 这套系统在价值链中的位置

一家电力公司向一个区域内每户家庭与企业售电，计量、按受监管的电价定价、按周期
出账。**电力营销 / 客户信息系统（营销 / CIS / 95598）**是商业内核：客户、电表、
抄表、电价、账单、收款，以及处理这一切后果的客户服务线路。

```
   客户 / 服务渠道                    受监管与网络边界
   ────────────────────────────        ─────────────────────────────
   营业厅                              电价与价格监管
   95598 热线                          配电系统（计量）
   网上 / 小程序门户                    SCADA / OMS 工单
   现场勘查与抄表                        收款 / 资金渠道
          │                                       ▲
          ▼                                       │
  ┌───────────────────────────────────────────────┴───────────────────┐
  │  营销 / CIS                                                    │
  │                                                                    │
  │  客户与账户主数据                                            │
  │  计量与抄表（含估抄）──▶ 电价引擎（版本化、生效日）  │
  │  出账与调整 ──▶ 审批工作流                                   │
  │  收款与对账                                                    │
  │  95598 服务与工单                                             │
  │  停复电（强护栏）                                               │
  └────────────────────────────────────────────────────────────────────┘
```

定义性约束是 `AGENTS.md` 中的一句话：**出账与对账数字必须可追溯到抄表，除已定义
的估抄规则外，零静默估算。**

本方案包的其余一切都源于这个事实：面向客户的数字不是平台可以去优化的商业
指标——它是**建立在计量之上的受监管算术**。

## 2. 电价计算是受监管的数学

`AGENTS.md`：电价规则必须**带版本、可审计、带生效日**。

三个属性，各有各的理由：

| 属性 | 为何承重 |
|---|---|
| **带版本** | 一次电价变更绝不能静默地重述已按旧费率开出的账单 |
| **可审计** | 算术必须可被重新推导——「这张账单为什么是这个金额？」是一个正当的问题，而且必须被回答 |
| **带生效日** | 费率在某一天变更；一个跨越该变更的周期必须让每段费率各自适用各自的时间段 |

因此本方案包把电价引擎当作一个**法定算术面**，而不是一份定价配置：

- 规则是受治理的制品，而不是随发布变化的代码；
- 账单存储所应用的**规则版本**，因此历史账单可复现；
- 一次变更是带日期、已发布的事件，背后有相应的权威。

> 与商业定价引擎（`omnichannel-commerce`）的差别是决定性的：在那里，价格是
> 平台去实现的商业决策；在这里，电价是**平台不得擅自「改进」的监管规定**。

> ⚠️ ASSUMPTION: 本方案包建模的是每个部署一套受监管电价制度。多档电价、
> 集中采购或零售竞争制度会改变引擎的形态，但不改变上述三个属性。

## 3. 计量：抄表、异常与估抄边界

账单从一个读数开始。`AGENTS.md` 点名了两条让这件事可信的控制：

**抄表异常** —— 缺失、超出合理范围或与历史不一致的读数不是一个可以被抹平
掉的数据问题；它是一个必须被暴露、并按既定规则解决的**异常**。

**估抄** —— 在无法取得实际读数的地方，可以代入一个估算——但只能由**既定
规则**产生，并且必须在这张账单上**可见**地标为估算，而不是当作实测呈现。

> 这条边界是承重的陈述。一个被静默代入的估算，会产生一张算术正确而事实
> 无据的账单——而客户无从知晓，供公司也无从举证。

> ⚠️ ASSUMPTION: 本方案包陈述估抄必须由规则定义且可见，但不指定估算方法。
> 该方法、其周期以及与下一次实际读数的对账，都是由监管决定的部署决策，本
> 方案包不指名任何方法。

## 4. 调整需要审批工作流

`AGENTS.md`：抄表异常**与**出账调整都需要审批工作流。

两者都是资金更正路径，危险之处也相同：一条可以被单方面应用的更正路径，就是
一个没有上界的财务控制。

因此工作流是一项**能力**，而不是流程偏好：

- 一次调整是一个显式、有归属、经批准的动作；
- 原账单保留，调整是一个新事件；
- 批准由具备相应权威的一方作出，并被记录。

> 这与 `telecom-bss` 的「重算，绝不编辑」以及 `omnichannel-commerce` 的受
> 幂等保护的资金操作是同一种纪律：一旦作出的财务断言，不会被改写。

## 5. 停复电遵循监管，并带护栏

`AGENTS.md`：停复电流程遵循**公共服务监管，并带严格护栏**。

停电不是带一个开关的催收动作——它是一个受监管的行为，对弱势客户、医疗设备、
季节与公共利益豁免都有后果。

本方案包的设计后果：流程必须把**护栏作为被强制的状态**承载，而不是当作
建议：

- **资格** —— 不得被停电的对象（受监管的豁免类别）；
- **通知** —— 行为之前必须的通知期；
- **时机** —— 受限时段（季节、一天中的时间、医疗需要）；
- **可审计** —— 决定及其依据的完整记录。

> 一个把资格规则持有为「某个人可能忽略的配置」的系统，并不符合它自己的护栏。
> 规则必须由流程求值，而不是由操作员记在心里。

> ⚠️ ASSUMPTION: 本方案包要求护栏**类别**作为被强制的状态存在，而不指名任何
> 具体的豁免类别、通知期或受限时段——那些来自监管，而不是来自本方案包。

## 6. 配电集成仅限接口

`AGENTS.md`：与配电系统的全部集成都**仅限接口，不含 SCADA 范围**。

这是一条有事实理由的范围边界：SCADA 是实时控制系统，有自己的安全与可用性
制度。一个伸手进入其中的商业系统，会继承一套它并非为承载而设计的约束。

边界画在接口处：

| 营销 / CIS 一侧 | 配电一侧 |
|---|---|
| 客户、账户、电表、读数、账单 | 网络拓扑、保护、开关 |
| 工单、服务请求 | OMS 故障管理与复电 |
| 95598 案件处理 | 影响客户的停电事件 |

> 接口是电力公司商业世界与运营世界相遇之处，而本方案包的立场是：这条接缝必须
> **显式且有契约**——不是因为两个系统不该协作，而是因为两者的失败语义不相容。

## 7. 核心流程（L1 视角）

1. **建档** —— 客户、账户、服务点、电表、电价分配。
2. **抄表** —— 通过自动采集或现场作业抄表；异常被提出，估抄只由规则产生且
   标注。
3. **计费** —— 在带生效日、带版本的规则下计算费用；账单记录规则版本。
4. **调整** —— 针对读数错误、电价变更或争议的更正，各自带审批工作流。
5. **出账与收费** —— 发票、支付渠道、对账。
6. **服务** —— 95598 案件、工单、现场派工、与停电关联的沟通。
7. **停复电** —— 只通过带护栏且可审计的流程。
8. **对账** —— 资金与电量可追溯到抄表。

## 8. 为什么这套系统格外难做对

- **这个数字是受监管的。** 它不可协商、不可优化，而它的算术必须多年之后仍
  可被重建。
- **读数是不完整的、迟到的、偶尔出错的。** 估算之所以存在是因为现实不完美，
  而每一个估算都是记录可以悄悄变得无据的地方。
- **资金更正是一个财务控制面。** 一条未经审批的调整路径就是没有上界的暴露。
- **停电是一个带人道主义边缘情形的受监管行为。** 规则复杂、随政策变化，而且
  不可省略。
- **周期会跨越变更。** 周期中途的电价变更、电表变更或服务变更必须被正确拆分，
  而不是被近似处理。
- **对账必须追溯到电表。** 资金与电量可追溯到读数，才让争议可裁决、审计可
  通过。

## 9. 定义质量指标

L1 框定意图；阈值在 L2 成为 NFR 目标。

| 指标 | 它回答什么 |
|---|---|
| 账单准确率争议率 | 算术是否站得住 |
| 估抄率及其在取得实际读数后的纠正偏差 | 估算是否被限定且诚实 |
| 抄表异常解决时长 | 异常是被暴露还是堆积 |
| 调整审批周期时间与拒绝率 | 控制是否既可用又可强制 |
| 账单周期准时率 | 受监管的时限是否被满足 |
| 电价规则版本时效 | 规则更新是否被正确地按生效日处理 |
| 停电护栏合规率 | 豁免是被强制执行还是只被记住 |
| 并网/配电接口可用性 | 这条接缝是否撑得住 |
| 抄表对账完整率 | 可追溯性规则是否成立 |

## 11. 本方案包在 L1 不会填上的空白

`AGENTS.md` 要求电价计算是「受监管的数学——带版本、可审计、带生效日」。那
是一个**框架**，而实际规则是监管性的。本方案包刻意不编码任何具体电价；在
`unverified` 状态下这样做，正是标准所禁止的臆造确定性。部署方的实际电价规则
是一个受治理的输入，而本方案包的职责是让它们的版本化、生效日与可审计性成为
结构性事实。
