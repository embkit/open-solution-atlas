# 01-business / 流程

> 电信 BSS/OSS 套件的流程定义。每个流程均说明其触发条件、
> 执行步骤，以及约束这些步骤的规则。规则位于
> `business-rules.md`（BR-xx）中，并在此引用，绝不重述。
>
> ⚠️ ASSUMPTION — 过程分解属于本方案包的设计。未引用任何
> 外部标准作为其依据。

## P-01 — 销售

| | |
|---|---|
| **触发条件** | 客户（或合作伙伴或渠道）接受一项产品提供物 |
| **结果** | 针对商业产品提供物创建的客户订单 |

1. 从**商业产品目录**中解析产品提供物（CAP-02）。
2. 解析其**规格说明**，明确其在资源层面的含义（CAP-03）。
3. 从资费计划中确定价格和资格条件；不查询任何网络详细信息（BR-05）。
4. 创建客户订单。

> 第 3 步就是 BSS/OSS 边界的商业端：定价在商业侧依据规格说明确定——绝不依据实时网络状态确定（BR-01）。

## P-02 — 分解

| | |
|---|---|
| **触发条件** | 存在客户订单 |
| **结果** | 在其涉及的各域中形成业务订单和资源订单 |

1. 沿规格说明从产品提供物追溯至相关服务实例。
2. 为每项服务创建一项**业务订单（SO）**。
3. 将每个 SO 按网络资源分解为**资源订单（RO）**。
4. 记录 CO → SO → RO 链，并建立双向链接（BR-04）。

> 这条链正是对“为何失败，以及我实际启用了什么”的回答。仅作为日志关联行存在的链不具备双向链接，无法满足 BR-04。

## P-03 — 履约

| | |
|---|---|
| **触发条件** | 存在资源订单 |
| **结果** | 资源已预留并激活，且已返回状态 |

1. 将每个 RO **仅通过接口**路由至 OSS 侧（BR-02）。
2. 预留资源、激活资源并报告状态；某个域可能失败，而其他域仍然成功。
3. 沿链向上将状态传播至 SO 和 CO（BR-04）。

> 部分完成的 RO 集合属于正常情况，而非异常。取消剩余部分是一个有状态问题，不得将其建模为回滚（BR-07）。

## P-04 — 计费

| | |
|---|---|
| **触发条件** | 发生使用或周期性事件，或者激活完成 |
| **结果** | 一条不可变的计费事件 |

1. 根据**按生效日期和版本管理的规则集**确定适用费用（BR-08）。
2. 生成一项**计费事件**——一经生成即不可变（BR-09）。
3. 将该事件关联至其订单、库存项和规则版本。

> 规则版本在生成时即被关联。后续规则变更不得重新表述已生成的事件，也不得使旧事件变得无法解释（BR-08）。

## P-05 — 出账

| | |
|---|---|
| **触发条件** | 账期结束 |
| **结果** | 一张可依据其事件重新生成的发票 |

1. 汇总该账期内的计费事件。
2. 应用调整——每项调整均须作为一项经**批准**的操作执行，同时保留原始账单（BR-10）。
3. 生成发票，**其中附带每项费用计算所依据的规则版本**（BR-11）。

> 发票的可重新生成能力是一项硬性要求，而非理想特性：相同事件加
> 相同规则版本必须生成相同发票。

## P-06 — 收款与催收

| | |
|---|---|
| **触发条件** | 发票逾期未付款 |
| **结果** | 付款已分摊，或已按应收款流程处理 |

1. 接受来自任何渠道的付款；按规则进行支付分摊。
2. 将逾期未付发票转入欠费催缴。
3. 升级至催收处理。

## P-07 — 服务与保障

| | |
|---|---|
| **触发条件** | 客户联系 95598，或故障影响客户 |
| **结果** | 一个具备真实上下文、已派发且已关闭的案例 |

1. 解析客户的真实情况：账户、表计、抄表历史、未付款项，以及任何将资源状态与商业关系关联起来的故障（BR-06）。
2. 创建故障单。
3. 通过 **BSS/OSS 接口**派发现场工作（BR-02）。
4. 记录解决结果并关闭。

> 第 1 步不得要求转接客户。无法看到表计和抄表上下文的客服界面不过是一本电话簿（BR-06）。

## P-08 — 对账

| | |
|---|---|
| **触发条件** | 按计划执行 |
| **结果** | 计费事件与**两侧**完成对账 |

1. 将计费事件与**订单**对账——可归属于所购内容（BR-12）。
2. 将计费事件与**库存**对账——使用归属于某个主体（BR-12）。
3. 消除差异：无主使用，以及无费激活。

> 只有在对账的**两个方向**上都执行时，对账才真正发挥关键作用。单向（订单 → 发票）会形成一个计费正确却对泄漏视而不见的系统（BR-12）。
