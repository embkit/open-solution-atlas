## 1. 一级能力

| # | 能力 | 它必须回答什么 | 备注 / L1 定位 |
|---|---|---|---|
| **CAP-01** | **客户与参与方** | 谁是商业交易对手 | 账户与协议是各自具有独立生命周期的对象 |
| **CAP-02** | **商业产品目录** | 我们销售什么 | 商业事实；由产品/商业职能所有 |
| **CAP-03** | **规格说明** | **产品提供物在资源层面的含义** | 目录之间的连接；一等对象，而非映射表 |
| **CAP-04** | **技术与资源目录** | 实际必须存在什么 | 独立于 02 的模型，绝不重复建模 |
| **CAP-05** | **码号资源库存** | 谁持有哪个号码，以及我们能否将其收回 | 有限且受外部监管的资源 |
| **CAP-06** | **订单管理与编排** | 客户购买时，端到端会发生什么 | CO→SO→RO 双向可追溯（`AGENTS.md`） |
| **CAP-07** | **计费与计费事件** | 按事件确定应付金额 | **不可变**，可同时与订单*和*库存对账 |
| **CAP-08** | **账单、开票与应收款** | 要求客户支付什么 | 可依据产生发票的事件进行重算 |
| **CAP-09** | **保障与客服** | 哪里出了问题、谁受到影响、承诺了什么 | 将资源状态关联回商业关系 |
| **CAP-10** | **对账、报告与隐私生命周期** | 各项内容是否一致，以及是否依法保留 | 双向对账；按类别保留/擦除 |

## 2. 边界（各项能力*不*负责什么）

| 能力 | 明确**不**属于其职责范围 |
|---|---|
| 02 商业产品目录 | 产品提供物如何在网络上实现——这属于 04，并由 03 连接 |
| 03 规格说明 | 定价或商业规则——这些由商业侧负责 |
| 04 技术与资源目录 | 向客户销售了什么——它描述*可以存在*的内容 |
| 05 码号资源库存 | 谁有资格持有号码——监管规则提供给 02 |
| 06 编排 | 对订单进行计费——它负责履约；由 07 负责计费事件 |
| 07 计费 | 归集为发票——这属于 08 |
| 08 账单 | 判断某项计费事件有误——更正必须创建**新事件**，绝不对原事件进行编辑 |
| 09 客服 | 更改网络状态——它负责提出请求并跟踪，由 OSS 执行 |
| 10 对账 | 决定结果——它负责检测差异；由人员和流程解决 |
| 10 报告 | 将底层数据加工为报告——报告派生自受治理的数据 |

> 三处边界支撑着本方案包。**02↔04**：若将二者合一，每次定价变更都会成为网络工程变更。**07**：通过编辑更正计费事件，是会破坏发票可复现性的失败模式。**10 单向对账与双向对账**：仅进行订单→发票对账，会形成能够正确计费、却对泄漏视而不见的系统。

## 3. 一级能力优先级

完整度足以支持讨论，但尚不足以支持估算；有意不涉及相对难度。

> ⚠️ ASSUMPTION: 之所以首先提及能力 **03 (规格说明)** 和 **10 (双向对账)**，是因为 `AGENTS.md` 将目录拆分和双向对账确定为本方案包的两项结构性承诺。此为编辑排序，并非有证据支持的关键性论断。

## 4. 整个平台的范围之外

- **网络本身**——网络元素、控制器、拓扑工程。
- **物理层协议**——ITU-T 符合性是**目录输入**，并非由本套件实现。
- **网络保障系统**——故障管理、性能监控；通过 BSS/OSS 契约集成。
- **欺诈检测**——作为信号使用，不属于本方案包的主题。
- **针对 CDR 的数据仓库分析**——属于 `data-ai` 方案包；本套件负责导出。
- **零售门店运营**——本套件为渠道提供服务；其本身并非零售门店。
