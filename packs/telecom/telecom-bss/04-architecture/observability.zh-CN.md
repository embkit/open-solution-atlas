## 绝不可权衡的五项不变量

`charge_event_mutated_attempt`、`traceability_missing_link`、
`rule_version_mis_split`、`guardrail_breach_attempt` 和
`invoice_not_regenerable` 必须为**零**。

不得以吞吐量或可用性为代价对这些不变量进行权衡，任何一项所导致的事故也不能仅通过修复症状来关闭。这里之所以有五项不变量，是因为这是一个受监管的计算领域：其中任何一项一旦被放宽，都会导致整个周期的金额静默出错，而非仅仅造成服务中断。

> 如果仪表板上的所有信号看起来都一样，团队就会形成权衡所有信号的习惯。
> 标明这些不变量可使这种权衡变得明确且可审查。

## 平台必须能够回答的问题

| 问题 | 回答依据 |
|---|---|
| “为什么向该客户收取了这笔费用？” | 计费事件、其规则版本和发票重算路径 |
| “该订单链路为何失败，我实际启用了什么？” | CO→SO→RO 链路，并沿两个方向追溯 |
| “费率变更后，本账期是否采用了正确版本？” | 经过评估并记录的跨账期拆分结果 |
| “为什么该客户被断开连接？” | 护栏评估记录及其输入项 |
| “谁授权了这项更正？” | 调整/冲抵审批记录 |
| “使用量或收入在何处失去归属？” | 双向对账及其泄漏发现结果 |

> 每个问题都可**依据平台自身的记录**回答，而非通过重建推算。
> 这正是仅追加存储旨在提供的特性。

## 追溯与关联

- **费率**追溯涵盖：事件接入 → 按生效日期解析规则 → 计费事件生成 → 发票汇总。每一步都携带规则版本，因此费率变更可归属于某个版本，而非某次发布。
- **订单**追溯涵盖：CO → SO → RO → 激活状态，并携带订单 ID，使部分完成情况可归属于某个域，而无须通过猜测确定。
- **客服**追溯涵盖：案例接入 → 上下文解析 → 分派 → 结案，并携带账户和计量表引用，从而可以验证“无需转接”的说法（NFR-010）。

## 告警策略

- **呼叫**：针对任何不变量违规，以及接口可用性低于 NFR-011 所规定水平的情况。
- **建单**：针对各侧的对账覆盖率、泄漏发现时长、账期延迟和保留期证据缺口。
- **复核**：每周复核调整/冲抵处理周期时长（NFR-008）：趋势上升意味着审批工作流正在被绕过，而这正是该控制措施旨在防止的失效模式。
