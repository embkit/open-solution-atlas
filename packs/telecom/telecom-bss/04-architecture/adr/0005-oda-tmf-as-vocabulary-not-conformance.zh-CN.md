# ADR-0005 — 采用 ODA 和 TMF Open API 作为词汇，而非声明符合性

- 状态：已接受
- 日期：2026-10-12
- 决策人：方案包维护者

## 背景

`AGENTS.md` 要求将 TM Forum ODA 组件词汇和 TMF Open API 系列作为本套件的规范性**接口语言**。

将公共标准用作接口语言有一项特定收益：生态系统的集成模式可以复用，而替换厂商意味着重新实现**标准**接口，而非专有接口。这正是 `stack_stance: stack-agnostic` 所承诺的。

问题在于此次采用*声称*了什么。公共标准有版本、成熟度级别、配置文件和符合性计划，而使用这些词汇并不能确立其中任何一项。

## 备选方案

1. **不采用标准；自行创造词汇**——速度最快，但会彻底放弃复用收益。替换厂商时仍需重新实现。
2. **采用词汇并声明符合性**——断言了尚未证实的事项。关于从未评估过的版本或成熟度级别的符合性声明，比不作声明更糟，因为这种声明会受到信赖。
3. **采用词汇；不声明符合性**——分解和接口名称来自标准；方案包明确声明，不主张任何成熟度级别或 API 版本。

## 决策

选择方案 3，并由 BR-14 和 FR-020 强制执行。

接口均采用已采纳的词汇来表达，而 BR-14 规定，声称未经评估的成熟度级别或 API 版本即属违规。这与医疗保健和 MLOps 方案包将治理框架作为*形态*采纳时的立场相同：采纳词汇，而非声明符合性。

## 后果

- 正面：接口语言公开且可复用，因此集成与厂商替换可以基于标准，而不是基于专有形态。
- 正面：方案包如实说明自身未知的事项。这一点很重要，因为未经审查的符合性声明会传播到采购文件中，而在采购文件中很难撤回。
- 负面：确实希望声明符合性的部署必须自行确立符合性，而本 ADR 不会为此提供任何起点优势。这是正确的——确立符合性是一项具有自身证据的独立行动——但这意味着词汇带来的部分收益要推迟到该行动中实现。
- 负面：词汇漂移。标准会不断演进，而锁定于某一版次的方案包将与之背离。本方案包不跟踪这种演进，且完全未指定任何版本；这是方案 3 的诚实后果。
