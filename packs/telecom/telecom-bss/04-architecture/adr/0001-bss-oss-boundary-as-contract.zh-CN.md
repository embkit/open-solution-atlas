# ADR-0001 — BSS/OSS 边界是集成契约，绝非权宜之计

- 状态：已接受
- 日期：2026-10-12
- 决策人：方案包维护者

## 背景

`AGENTS.md` 要求商业侧（BSS）与资源/履约侧（OSS）之间的边界必须明确保持为集成契约，绝不模糊化。

在大多数软件中，服务边界只是实现细节。这里并非如此，因为两侧回答的是不同问题，响应速度不同，失败语义也不同：

| | BSS | OSS |
|---|---|---|
| 回答的问题 | *我们卖出了什么，以及我们欠付了多少钱？* | *服务此刻是否切实存在？* |
| 单位 | 商业产品、客户订单、发票 | 逻辑/物理资源、业务订单 |
| 延迟 | 秒到天 | 毫秒到分钟 |
| 失败后果 | 金额错误、争议、发票冲抵 | 服务中断、SLA 违约 |

模糊边界的压力往往来自一片好心：商业层“仅仅需要知道”网络是否正常；履约侧也“仅仅需要知道”该收取什么费用。

## 备选方案

1. **权宜模糊化**——双方各自在觉得方便时调用对方。这样做速度很快，却会将实时控制职责迁入原本并非为承载这些职责而设计的商业系统，并将商业决策权迁入运营侧。
2. **跨边界共享数据库**——避免设置接口，却将双方的可用性绑定在一起，并使边界成为可配置项而非契约。
3. **显式接口契约**——所有集成均通过明确声明且纳入版本管理的接口进行，并明确规定载荷结构、状态词汇、时序、所有权和失败语义；以其他任何方式跨越边界均属于缺陷。

## 决策

采用方案 3，由 BR-01（商业决策绝不查询网络状态）、BR-02（仅限接口，不涉及 SCADA 范围）、FR-012、FR-013 和 CTL-06 强制执行。

商业侧通过规格说明这一对象了解产品提供物在资源层面的含义（ADR-0002）。商业层不读取网络状态来回答商业问题，运营侧也不计算费用。

## 后果

- 正面：控制职责不会意外迁入商业系统；各侧的故障模式仍归各侧自身；OSS 故障可归因于 OSS，而非 BSS 套件（NFR-011）。
- 正面：跨边界接缝变得可测试。无法声明其载荷结构、状态词汇、时序、所有权和失败语义的集成就是耦合，而声明要求会在设计阶段将其发现。
- 负面：某些确实有用的问题更难回答——“今天能否向该客户承诺此速率？”必须通过指定的接口调用获取，或者如实回答“未知”。本方案包选择如实返回*未知*（`integration.md` 故障模式契约），而不是为图方便直接读取。
- 负面：接口必须进行版本管理并持续维护，这是一项长期性工作。耦合今天成本更低，但日后的成本无上限。
