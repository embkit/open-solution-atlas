# 00-context / 行业简报 — 电信 BSS/OSS 套件

## 1. 本系统在价值链中的定位

电信运营商销售的服务必须实际触达网络。**业务支撑系统（BSS）**是商业层——负责销售、定价、计费、收款和支持。**运营支撑系统（OSS）**是履约层——负责在网络上实现该服务。

正如 `README.md` 所述，定义性的问题是**订单到收款与订单到激活的一致性**：目录销售的内容、订单编排器所履行的内容、计费所收取的费用，以及网络实际激活的内容，必须在长期运行、跨多领域的过程中始终保持一致。

```
   商业层（BSS）                           履约层（OSS）
   ──────────────────────                    ───────────────────────
   客户与参与方                              网络库存
   商业产品目录                              资源库存
   定价/资费计划                             开通自动化
   订单录入与分解 ──────────────────────────▶ 激活/预留
   计费与账单                                网络编排
   开票与应收款（欠费催缴）                   保障/故障管理
   客服                                      号码/码号池
            │                                        ▲
            └──────── 由规格说明保障 ◀────────────────┘
                       连接两个目录
```

方案包是**套件**，而非单个系统：一组领域必须就同一商业对象在从产品提供物到发票再到激活的流转过程中保持一致。

## 2. 绝不模糊化的边界

`AGENTS.md` 将 **BSS/OSS 分离视为一项集成契约**，明确规定“绝不模糊化”。

这并不常见。在大多数软件中，服务边界是实现细节。这里却并非如此，因为两侧回答不同的问题、响应速度不同、失败语义也不同：

| | BSS | OSS |
|---|---|---|
| 所回答的问题 | *我们卖出了什么，以及我们欠付了多少钱？* | *服务此刻是否切实存在？* |
| 单位 | 商业产品、客户订单、发票 | 逻辑/物理资源、业务订单 |
| 延迟 | 数秒至数天（账期） | 数毫秒至数分钟 |
| 失败后果 | 金额错误、争议、发票冲抵 | 服务中断、SLA 违约 |
| 正确性取决于 | 目录与协议 | 网络的实际状态 |

因此，两者之间的契约是**规格说明**——这个对象说明商业产品在资源层面意味着什么。一旦边界模糊化——让 BSS 谈论网络，或让 OSS 谈论价格——此后每一次对账都会变成定制化工作。

## 3. 两个目录，一份规格说明

`AGENTS.md`：商业产品目录和技术与资源目录是**由规格说明连接的不同模型，而非重复模型**。

这是第二项结构性承诺；若违反这一承诺，就会出现一种特定的失败模式。如果两个目录采用同一模型：

- 每次商业定价变更都会成为面向网络的变更，反之亦然；
- 仅含资源的产品（批发、互联互通、M2M SIM）将没有商业表示，或者获得一个虚假的商业表示；
- 商业发布周期将受网络工程周期的闸门约束。

```
   商业目录                         规格说明                         技术/资源目录
   ─────────────────                 ─────────────                ────────────────────────
   产品提供物  ─────────────▶  此产品提供物在资源层面           逻辑资源
   资费计划                       的含义及其验证方式  ──▶         物理资源
   资格规则                                                      拓扑/激活路径
   捆绑、促销                                                               │
                                                                              ▼
                                                    一个产品提供物 → N 种资源实现
```

> 规格说明是连接点，也是产品与网络转换的所在之处。“这个客户实际上拥有什么”的答案也源于此，因此术语表将其视为一等对象，而不是映射表。

## 4. 订单分解是一条可追溯链

`AGENTS.md`：从**客户订单 → 业务订单 → 资源订单**进行的订单分解必须**端到端可追溯**。

```
   客户订单（CO）   “我想要这个”
        │  分解
        ▼
   业务订单（SO）    “涉及这些服务实例”
        │  按服务编排
        ▼
   资源订单（RO）   “必须预留/激活这些网络资源”
        │
        ▼
   激活状态  ──▶ 反向传播至 SO 和 CO
```

可追溯性要求并非簿记工作。它是回答以下三个问题的唯一方式，而这三个问题决定系统是否有效：

1. *为什么会失败？*——从 CO 追溯到未完成的 RO。
2. *客户为什么在为它付款？*——从发票行追溯到 CO 和产品提供物。
3. *我究竟启用了什么？*——从资源订单追溯到发生变化的库存项。

无法沿两个方向逐步追溯的订单，会使上述三个问题都只能沦为组织内部的考古工作。

## 5. 计费事件不可变，且可双向对账

`AGENTS.md`：计费/账单事件**不可变**，并且**可与订单和库存双向对账**。

这两项属性各有不同的原因：

- **不可变**——费用是一项财务断言。重算账单会生成新事件，而不是改写原事件，因为旧的断言已经告知客户。
- **可与订单对账**——因为费用必须能够归属于所购内容。
- **可与库存对账**——因为资源的使用归属于某个客户，而无人计费或被重复计费的资源属于缺陷，只有库存侧能够发现。

> 双向对账是承重属性。单向对账（订单 → 发票）会产出能够正确计费却无法检测泄漏的系统；另一方向则能发现无主使用和无费激活。

## 6. 接口：以 ODA 和 TMF Open API 作为规范语言

`AGENTS.md` 采用 **TM Forum ODA 组件词汇**和 **TMF Open API 系列**作为规范接口语言。

这是两项各自独立的标准，用途各不相同：

| | 标准化内容 | 本方案包的用法 |
|---|---|---|
| **ODA（Open Digital Architecture）** | **组件词汇**——如何将领域分解为具有公开契约的组件 | 架构分解所用的词汇 |
| **TMF Open APIs** | **接口系列**——客户、目录、业务订单与资源订单、计费、资源、故障单 | BSS 各领域之间以及 BSS 与 OSS 之间的接口语言 |

> 使用公开标准作为接口词汇有一项特定收益：生态系统中的集成模式可以复用，更换供应商意味着重新实现**标准**接口，而不是专有接口。这是方案包依据自身术语作出的 `stack_stance: stack-agnostic` 决策。

## 7. 核心流程（L1 视图）

1. **销售**——针对商业产品提供物录入客户订单，并解析资格规则和定价。
2. **分解**——将订单分解为其所涉及各领域中的业务订单和资源订单。
3. **履约**——OSS 侧预留并激活资源，通过编排链回传状态。
4. **计费**——对使用量和周期性事件进行计费，形成计费事件。
5. **出账**——费用按账期汇总为发票；调整/冲抵均为新事件。
6. **收款**——应收款随着账龄进入欠费催缴、支付分摊和催收流程。
7. **支持**——通过故障单和保障，将资源状态关联回商业关系。
8. **对账**——订单 ↔ 计费事件 ↔ 库存，双向进行。

## 8. 为什么本系统尤其难以正确实现

- **商业对象长期存在且可变。** 客户的产品实例会存在多年，价格会变化，资源会变化，并持续重新计费——与此同时，产生该实例的定义可能已经停用。
- **跨多领域的编排与部分失败。** 涉及五个领域的订单会部分失败，而“取消其余部分”是一个有状态问题，无法通过简单回滚解决。
- **资金必须可复现。** 多年以后，发票仍必须能够依据产生它的事件并按照当时适用的定价重新生成。
- **号码是稀缺且受监管的库存。** 号段、编码和端口是有限的公共资源；分配、释放和携号转网规则来自外部且会发生变化。
- **商业/技术分界不能合并。** 促成二者合并的压力始终存在，因为保持规格说明最新确实是实际工作——而其成本会在尚未出现任何问题时显现。

## 9. 定义质量指标

L1 界定意图；阈值在 L2 成为 NFR 目标。

| 指标 | 回答的问题 |
|---|---|
| 订单到激活交付时长（p50/p95） | 整条链是否完成 |
| 按领域和原因划分的订单异常落项率 | 问题出在编排还是某个特定领域 |
| 账期按时完成率 | 资金是否按计划产生 |
| 计费事件对账率（对比订单和库存） | 能否检测到泄漏 |
| 发票争议率 | 面向客户的数字是否可信 |
| 欠费催缴回收率及成本 | 应收款是否确已收回 |
| 目录发布周期时间（商业与技术） | 两个目录是否仍能跟上发布节奏 |
| 码号资源库存碎片化程度（已分配与可用） | 资源是否正在被浪费 |
