# 03-domain / 术语表

> 此处定义的术语在本方案包中含义唯一；后文不会引入同义词。`Source` 记录依据：**[ODA]** TM Forum Open Digital Architecture 词汇（采用，并非声称遵循）、**[TMF]** TMF Open API 系列（采用，并非声称遵循）、**[AGENTS]** 本方案包的 `AGENTS.md` 设计立场、**[PACK]** 本方案包的定义、**[CONV]** 行业惯例。

## 1. 两侧与边界

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **BSS** | 业务支撑系统 | 商业层：销售、定价、出账、收款、支持。反映*我们卖出了什么，以及我们欠付了多少钱*的系统。 | [AGENTS] |
| **OSS** | 运营支撑系统 | 履约与保障层：*服务此刻是否切实存在*。 | [AGENTS] |
| **BSS/OSS boundary** | BSS/OSS 边界 | 二者之间的集成契约，通过**规格说明**表达。绝不可模糊化。 | [AGENTS] |
| **Blurred boundary** | 边界模糊化 | 允许 BSS 谈论网络，或允许 OSS 谈论价格。这种失败会使之后每次对账都变成定制化工作。 | [PACK] |

## 2. 目录与规格说明

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Commercial product catalog** | 商业产品目录 | 商业层面的事实：提供什么、以什么价格、向谁提供，以及适用什么资格条件。 | [AGENTS] |
| **Technical / resource catalog** | 技术与资源目录 | 为使产品提供物切实存在，网络中实际必须存在什么。 | [AGENTS] |
| **Specification** | 规格说明 | 将二者连接起来的对象：商业产品提供物在**资源层面意味着什么，以及如何验证**。它是一等对象，而非映射表。 | [AGENTS] |
| **Product offering** | 产品提供物 | 可销售的商业产品与其规格说明的组合。 | [ODA]/[CONV] |
| **Price plan** | 资费计划 | 附加于产品提供物的商业定价。此处的变更**绝不**是面向网络的变更。 | [PACK] |
| **Eligibility rule** | 资格规则 | 谁可以购买，以及须满足哪些前提条件。 | [CONV] |
| **Resource realisation** | 资源实现 | 使产品提供物成为现实的 N 种技术方式之一。一个产品提供物可以映射到其中多种。 | [PACK] |
| **Duplication (anti-pattern)** | 目录重复 | 将两个目录建模为一个。这种压力始终存在，因为保持规格说明最新确属实际工作；其成本会在尚未出现任何问题时显现。 | [PACK] |

## 3. 订单与编排

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Customer order (CO)** | 客户订单 | 客户在产品提供物层面提出的商业请求。 | [CONV] |
| **Service order (SO)** | 业务订单 | 列明所涉及服务实例的分解步骤。 | [CONV] |
| **Resource order (RO)** | 资源订单 | 列明需预留或激活的网络资源的步骤。 | [CONV] |
| **Order decomposition** | 订单分解 | CO → SO → RO，按服务、按域进行。 | [AGENTS] |
| **End-to-end traceability** | 端到端可追溯 | 整条链可沿**两个**方向追溯：CO→RO 用于诊断故障，发票→CO 用于确定费用归属，RO→库存用于确认实际落地。 | [AGENTS] |
| **Orchestration** | 编排 | 驱动分解后的订单跨域流转，并处理部分失败。 | [CONV] |
| **Partial failure** | 部分失败 | 分解完成了部分域、但未完成其他域的情形。不能以简单回滚处理；这是有状态的问题。 | [PACK] |
| **Fallout** | 异常落项 | 已停止的订单步骤。它是**可诊断**单元，而非重试队列。 | [PACK] |
| **Re-drive** | 重新驱动 | 在不重复产生费用或执行激活的情况下，重新启动异常落项步骤。 | [PACK] |
| **Order-to-activation** | 订单到激活 | 商业承诺成为网络现实——需加以跟踪，而非靠假定。 | [PACK] |

## 4. 资金：计费、费用与账单

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Rating** | 计费 | 将使用量和周期性事件转换为计费事件。 | [CONV] |
| **Charge event** | 计费事件 | 一条不可变的断言，表明存在应付费用。**生成后绝不修改。** | [AGENTS] |
| **Recompute, not edit** | 重算不改写 | 更正一项费用时应创建新事件；如果客户已被告知，则应创建调整/冲抵——绝不进行原地更改。 | [AGENTS] |
| **Adjustment / credit** | 调整/冲抵 | 用于更正先前事件的新财务事件。先前事件仍然保留，并且仍可复现。 | [PACK] |
| **Bill cycle** | 账期 | 计费事件汇总为一张发票的周期。 | [CONV] |
| **Invoice regeneration** | 发票重算 | 依据产生历史发票的事件，并使用当时适用的定价，重新构建该发票。这是硬性要求，而非理想特性。 | [PACK] |
| **Dunning** | 欠费催缴 | 通过联系、限用和断开连接，对未付款发票进行欠费催缴。 | [CONV] |
| **Payment allocation** | 支付分摊 | 按最早优先或既定策略，将付款分摊至发票。 | [CONV] |
| **Collections** | 催收 | 针对逾期应收账款采取追偿行动。 | [CONV] |
| **Interconnect settlement** | 互联结算 | 运营商之间的批发与漫游结算。与零售计费分属不同的资金流。 | [CONV] |

## 5. 号码、资源与对账

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Logical resource** | 逻辑资源 | 服务层视角下必须存在的对象。 | [ODA]/[PACK] |
| **Physical resource** | 物理资源 | 网络元素层视角下实际存在的对象。 | [ODA]/[PACK] |
| **Activation path** | 激活路径 | 实现产品提供物的具体序列，包括失败情形和替代方案。 | [PACK] |
| **Number / code inventory** | 码号资源库存 | 号码、编码和号段构成的资源池——一种有限且受外部监管的资源。 | [PACK] |
| **Allocation / release** | 分配/释放 | 号码的分配与回收。释放才是稀缺能力：未释放的号码会造成无声泄漏。 | [PACK] |
| **Fragmentation** | 碎片化 | 因释放策略失败而形成的已分配但不可用号码。是一项浪费指标。 | [PACK] |
| **Portability** | 携号转网 | 依据外部规则，在运营商或服务之间迁移号码。 | [CONV] |
| **Two-way reconciliation** | 双向对账 | 将计费事件与**订单**（可归属于所购内容）及**库存**（使用归属于某个主体）**同时**进行对账。 | [AGENTS] |
| **One-way reconciliation** | 单向对账 | 仅进行订单→发票对账。由此形成的系统能够正确计费，却**对泄漏视而不见**。 | [PACK] |
| **Usage with no customer** | 无主使用 | 无法归属于任何用户的使用消耗。只有库存侧能够发现。 | [PACK] |
| **Activation with no charge** | 无费激活 | 已实现但未计费的资源。只有订单侧能够发现。 | [PACK] |

## 6. 客服、保障与隐私

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Trouble ticket** | 故障单 | 客服侧的问题，与服务实例关联，进而与商业关系关联。 | [CONV] |
| **Service instance** | 服务实例 | 针对一个客户的一项产品提供物的实现——客服和计费共同引用的对象。 | [PACK] |
| **Assurance** | 保障 | 保持服务真实有效的活动：监控、检测、修复、反馈。 | [CONV] |
| **Retention class** | 保留类别 | 与数据类别（通话详单（CDR）、位置/使用、客户主数据、发票、客服历史）关联的明示保留与擦除策略，而非全局设置。 | [AGENTS] |
| **Generation window** | 生成/再生窗口 | 历史记录（例如发票）可依据事件重新生成的时间范围。它与擦除要求存在张力；解决该问题的机制是按类别制定策略。 | [PACK] |
| **CDR (call data record)** | 通话详单 | 高容量、准静态的使用记录；保留量最大的保留类别。 | [CONV] |
| **Subscriber** | 用户 | 数据所指向的个人——隐私主体，有别于客户（商业交易对手）。 | [PACK] |

## 7. 约定

- **“不得”**标记违反后即构成缺陷的规则——计费事件不得修改；两个目录不得合并为一个；BSS/OSS 边界不得模糊化；已释放的号码不得仍保持已分配状态。
- **无同义词**：本方案包使用**计费事件**表示不可变的财务断言，使用**发票**表示汇总产物；使用**业务订单**和**资源订单**表示两个分解层级，绝不单独使用“订单”；使用**逻辑资源/物理资源**表示技术目录的两个视图。
- **采用词汇，而非声明符合性。** ODA 和 TMF Open API 名称被采用为本方案包的词汇；本文不主张符合任何成熟度级别或 API 版本。
