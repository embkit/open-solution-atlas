# 04 · 可观测性

> 测量什么、系统必须能够回答什么，以及每项信号各自的
> *用途*。各项信号都可追溯到其所衡量的 NFR。
>
> ⚠️ ASSUMPTION — 信号选择和阈值属于方案包的设计范围。

|---|---|---|
| **oversell_detected** | NFR-001 | **sev-1** — 头号大忌 |
| **snapshot_mutated_attempt** | NFR-004 | **sev-1** — 正确性不变量 |
| **duplicate_money_effect** | NFR-005 | **sev-1** — 正确性不变量 |
| **availability_mismatch** | NFR-002 | sev-2 |
| **reservation_release_lag** | NFR-003 | sev-2 |
| **snapshot_charge_variance** | NFR-007 | sev-2 — 客户可见的数字有误 |
| **gap_age** | NFR-009 | 超过阈值后为 sev-2 |
| **checkout_latency_p95/p99** | NFR-006 | sev-3（持续出现时为 sev-2） |
| **cross_channel_visibility_lag** | NFR-010 | sev-2 |
| **refund_cycle_p95** | NFR-008 | sev-3 |
| **channel_onboarding_cycle** | NFR-012 | sev-3 |
| **pci_evidence_completeness** | NFR-011 | **sev-1** — 支付合规范围声明缺乏证据支撑 |

## 三个属于正确性不变量而非服务级别的信号

`oversell_detected`、`snapshot_mutated_attempt` 和 `duplicate_money_effect`
必须为**零**。不得拿延迟或可用性与这些不变量进行权衡；由其中任何一项引发的
事故，不能通过修复症状来关闭。

> 这一区分在实践中很重要：如果仪表板中的所有信号看起来都
> 一样，就会让团队习惯于把所有信号都拿来权衡。标出这些不变量
> 可以让权衡变得明确且可复核。

## 平台必须能够回答的问题

| 问题 | 回答依据 |
|---|---|
| “哪些订单发生了超卖，原因是什么？” | `oversell_detected` + 预留与消耗事件链 |
| “为什么向该客户收取的金额不同？” | 价格快照、其规则集版本，以及由其生成的请款事件 |
| “此次重试是否导致重复扣款？” | 幂等键，以及共享该键的资金操作记录 |
| “该订单目前位于何处，可以在哪个渠道看到？” | 逐行履约状态和跨渠道可见性信号 |
| “预期情况与实际情况有何差异，是否已经关闭？” | 账本、实际值数据流，以及未结对账差异的存续时长 |
| “我们能否证明卡数据从未进入该渠道的平台？” | 按渠道划分的 PCI 证据记录 |

> 每个问题都**依据平台自身的记录**回答，而不是通过事后重建。这正是账本、快照和事件日志
> 存在所要提供的特性。

## 追溯与关联

- 一次结算追溯涵盖：定价评估 → 快照冻结 → 授权 →
  消耗 → 创建订单 → 追加至账本。每个步骤都携带订单 ID、
  快照 ID，并在存在时携带幂等键。
- 跨渠道追溯携带订单 ID 和渠道，因此可见性延迟
  可归因于传播延迟，而不是靠猜测判断。

## 告警策略

- **呼叫**：任一不变量被违反（上述三项）、PCI 证据
  不完整，或可用库存不匹配超出数量阈值时。
- **创建工单**：延迟、对账差异存续时长和周期时长达到阈值时。
- **复核**：每周复核跨渠道可见性延迟 p95；呈上升趋势是渠道分叉核心（BR-14）的早期
  迹象。
