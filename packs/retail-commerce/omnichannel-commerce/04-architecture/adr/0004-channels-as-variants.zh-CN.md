# ADR-0004 — 渠道是共享核心之上的变体，绝非分叉

- 状态：已接受
- 日期：2026-10-12
- 决策人：方案包维护者

## 背景

`AGENTS.md` 规定，小程序和 POS 均是渠道变体。渠道引入的时间不同、由不同团队构建，并各有自己的惯例——因此，分叉的压力按渠道存在，既直接又持续不断。

分叉的失败之处并非技术回归。它会使全渠道承诺悄然落空：客户在线下单，门店却看不到该订单；客户到店退回在线订单，退款却无归属；“一个数字、一个价格、一份承诺”这一特性也会从平台实际提供的能力，变成业务自行宣称的承诺。

## 备选方案

1. **允许渠道分叉**——各渠道上线最快。每个分叉起初只是一条捷径，最终却会变成第二套订单系统，拥有自己的状态术语体系、库存策略和对账机制。
2. **一个不作区分的核心加渠道标志**——避免重复，但会将渠道条件分支置于核心内部；这些分支会不断叠加，并且无法按渠道分别测试。
3. **共享核心 + 实现已声明契约的渠道适配器**——核心负责商品、价格、库存、订单和资金；渠道声明其输入、支付路径、身份处理和履约来源，其适配器实现该契约。

## 决策

选择方案 3，由 BR-14、FR-001、FR-002、FR-016、FR-025 以及 `04-architecture/integration.md` 中的渠道契约强制执行。

核心对象——商品、价格、库存、订单和资金——均为共享。渠道的差异体现在**输入**、**履约来源**和**身份处理**上；任何渠道特定行为都必须是适配器解析的变体配置，否则就不应存在。

渠道接入设有闸门（FR-025、FR-026）：无法声明契约全部五个方面的渠道不属于变体。

## 后果

- 正面：新增渠道只需配置和适配器，而非开展一个项目；订单状态机、价格快照和账本统一适用，因此不会出现“为什么门店看到的数字不一样？”的问题。
- 正面：该不变量可度量。跨渠道可见性延迟（NFR-010）和接入周期时长（NFR-012）是分叉在实践中开始形成的早期信号，能够在其尚未出现在架构中之前予以识别。
- 负面：每个渠道都必须契合该契约，其中一些渠道无法自然契合。本方案包的立场是，此类渠道要么经过适配，要么不予接入——分叉不是第三种选择。
- 负面：渠道变更自身 API 时，必须同步维护适配器。这是实际存在的经常性工作；成本虽低于分叉，但并非没有成本。
