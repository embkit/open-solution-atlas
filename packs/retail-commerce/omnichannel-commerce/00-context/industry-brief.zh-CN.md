# 00-context / 行业简报 — 全渠道商业与订单平台

## 1. 本系统在价值链中的位置

顾客可以从网站、小程序、门店、电商平台和电话购买同一款产品，同时期待价格统一、库存统一、订单历史统一，并对到货时间作出统一承诺。

**全渠道商业与订单平台**是让这五个触点成为同一业务的系统：商品目录、购物车、结账、定价、库存、订单、履约，以及贯穿所有这些能力的支付抽象。

```
   渠道                                  共享平台核心
   ────────                              ───────────────────
   网上商店            ┐
   小程序              ┤              产品主数据 (PIM)
   移动应用            ┼────▶          购物车与结账
   门店 POS            ┘              促销引擎 (快照定价)
   电商平台商品信息                     库存服务 (稀缺资源)
   电话 / 社交 / 代理                   订单与履约编排
                                        支付抽象 (PSP 托管)
                                               │
                                               ▼
                                      一个数字、一个价格、一项承诺
```

决定性约束可以概括为一句话：**超卖是头号大罪**（`AGENTS.md`）。本方案包中的其他一切，都是为了让这一句话在由不同时期的不同团队构建、且失败模式各异的渠道之间都成立。

## 2. 库存扣减是语义决策，而非配置

`AGENTS.md` 将订单状态机**以及**库存扣减语义列为决定系统成败的关键决策。

关键在于，“我们何时扣减库存？”并没有一个显而易见的正确答案。每种选择都是一场不同的业务押注：

| 扣减时点 | 它换来什么 | 它带来什么风险 |
|---|---|---|
| **加入购物车时** | 确保购物车中的商品仍可购买 | 弃购购物车会占用库存；机器人囤货 |
| **订单确认时** | 为正在付款的顾客保留库存 | 支付失败或放弃支付会占用库存 |
| **支付捕获时** | 可避免虚假占用 | 顾客已付款，却发现库存已无——造成面向顾客的超卖 |
| **开始履约时** | 仅真正的订单承诺才占用库存 | 顾客看到的确认信息可能早已有误 |

扣减本身的语义——预留还是消耗、部分释放、到期、跨渠道迁移——与扣减时机同样重要：

- **预留**是可逆的；已预留但从未支付的购物车必须正常到期或被放弃，不留下任何占用。
- **消耗**不可逆；商品已经承诺发货。
- **跨渠道**订单（线上购买、门店自提）必须只在一个地点扣减一次，不能在两个地点各扣一次。

> 平台的职责是让这一选择**明确且按产品划分**——把占用策略作为产品定义的一部分——而不是设置一个全局开关，碰巧对大多数商品正确，却对其余商品造成灾难性后果。

## 3. 订单状态机：正确性层面，而非工作流

订单不只是一个状态字段。它是一个有状态对象，必须在每个渠道、每个时点都一致地作出判定，包括在部分失败的情况下：

- *已付款但尚未接单？*——款项已收，履约尚未开始。
- *已接单但库存已无？*——应当取消，并且可能已经需要退款。
- *已发货但退货配送员中止配送？*——跨渠道逆向处理正在进行中。
- *部分履约？*——部分订单行已发货，部分已取消，部分已退款。

本方案包将状态机视为**核心**关键构件，因为每项下游能力（支付、履约、会员权益、客服）都要读取它；而状态不明确的订单会直接给顾客带来后果，而不只是产生一条日志记录。

> ⚠️ ASSUMPTION: 本方案包假设状态机在**各渠道一致地对外暴露**——采用相同的状态名称、相同的状态转换和相同的时间戳——因为小程序/POS 被明确视为**渠道变体**，而不是各自采用不同词汇的独立订单系统。

## 4. 资金操作需要幂等键和对账

`AGENTS.md`：每项资金操作都需要幂等键和对账规范。

在商业交易中，重试不是错误路径，而是正常路径。顾客可能重复点击，PSP 可能在扣款后超时，webhook 投递也可能被重复发送。重复扣款的后果不是日志异常，而是退款、争议和支持工单。

由此产生两项要求：

- 每项资金流转操作都要有**幂等键**；其作用域应使同一时间窗口内的重试合并为一次，并且该键应属于平台自身，而不是 PSP。
- 每条资金流都要有**对账规范**：对照预期与实际，并将差异的弥合自动化，而不是靠事后调查。对账不是报告，而是**规范**——一项明示的预期和一套差异处理程序。

> ⚠️ ASSUMPTION: 本方案包假设幂等键由平台而非 PSP 产生，并且 PSP 自身的幂等机制并不充分，因为它无法覆盖另一条集成路径（POS 终端、电商平台）。

## 5. 必须以可证明的方式将 PCI 范围排除在核心之外

`AGENTS.md`：必须通过 PSP 托管字段，以可证明的方式将 PCI 范围**排除在核心之外**。

“范围之外”是一项必须加以证明、不能仅凭声称的主张。惯常的证明方式是架构层面的：卡数据绝不进入平台自身流程，因为相关字段由 PSP 呈现，而平台自始至终只会看到一个令牌。

之所以将其列为设计要求，是因为替代方案——由平台处理卡数据并被审计判定为处于范围内——会改变整个架构（分段、日志记录、评估周期）。这一决策必须在开始时一次作出，之后无法通过改造补上。

## 6. 促销基于定价快照进行评估

`AGENTS.md`：促销基于**定价快照**进行评估，订单捕获后绝不重新计算。

一旦会重新计算的促销，顾客就可能在付款过程中失去该促销。如果规则发生变化、活动范围被重新界定，或者捕获后折扣被错误应用，面向顾客的数字就会不同于先前展示的数字。

因此，快照会在捕获时冻结以下内容：

- 商品价格及其来源；
- 已应用的促销，以及各自经评估后产生的贡献；
- 每种货币、每条订单行的总额；
- 生成该结果的规则集版本标识。

> 这与 `growth-analytics` 事件模式和 `telecom-bss` 发票重新生成遵循同样的原则：**数字必须能够在事后复现**，否则每起争议都无从解决。

## 7. 小程序和 POS 是渠道变体

`AGENTS.md`：小程序/POS 是**渠道变体**——不是独立系统。

这是一项具有具体后果的设计立场：

- 订单模型、库存模型、定价模型和状态机均为共享；
- 渠道之间的差异体现在**输入**（订单如何到达）、**履约**（订单发往何处）和**身份**（顾客是谁），而不在核心对象上；
- 渠道特定行为必须是**变体配置**，而不是分叉。

分叉核心的渠道会造成典型的全渠道故障：顾客在线下单，门店却看不到；顾客到店办理线上订单退货，退款却没有归属。

## 8. 核心流程（L1 视图）

1. **浏览**——商品目录和搜索，与渠道无关，并按渠道呈现。
2. **定价**——依据实时规则评估促销，生成**快照**。
3. **购物车**——加入商品、定价，并根据产品的占用策略决定是否预留。
4. **结账**——通过 PSP 托管字段采集配送信息、身份信息和支付信息。
5. **授权与捕获**——在幂等键控制下执行资金操作。
6. **扣减**——依据策略，在一个地点预留或消耗库存。
7. **履约**——路由、发货、门店自提或配送。
8. **售后**——退货、退款、取消——各自都有独立的状态转换和资金操作。
9. **对账**——核对每项资金和库存变动的预期值与实际值。

## 9. 为什么这个系统格外难以处理妥当

- **并发问题，无处不在。** 两位顾客、两个渠道、最后一件商品。真正棘手的故障是竞态，而且只有在负载下才能复现。
- **部分失败是常态，而非边缘情况。** 支付成功，库存失败；库存成功，配送失败；配送成功，顾客在运输途中取消。
- **回退并非简单的逆操作。** 退款不是一笔负向扣款，退货也不是一笔负向发货，而且二者都会与可能已经再次售出的库存交互。
- **渠道在不同时期接入。** 每个新渠道都是一个变体，而按渠道分叉核心的诱惑会立即出现，并造成致命后果。
- **促销可以组合。** 叠加、互斥和按渠道划分的资格条件会转化为规则问题，而清楚表达规则就是产品本身。
- **资金必须可复现、可逆。** 每个向顾客展示的数字都是平台必须能够兑现、解释并重新推导的承诺。

## 10. 定义质量指标

L1 界定意图；在 L2 阶段，阈值将成为 NFR 目标。

| 指标 | 回答的问题 |
|---|---|
| 超卖/负库存率 | 超卖这一头号大罪是否发生 |
| 库存准确率（系统与实物） | 盘点结果是否可信 |
| 重复扣款/重复退款率 | 幂等机制是否有效 |
| 订单承诺差异（展示值与实际值） | 定价快照是否保持一致 |
| 促销错误/覆写率 | 促销规则是否表述正确 |
| 按渠道划分的结账转化率 | 核心是否服务每个变体 |
| 退货和退款周期时间 | 回退是否易于处理 |
| 对账积压和差异账龄 | 差异是否得到消除 |
| 跨渠道连续性（订单处处可见） | 核心是共享还是已分叉 |
