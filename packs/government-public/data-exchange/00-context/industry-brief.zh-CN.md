# 00-context / 行业简报 — 政务数据共享交换平台

## 1. 本系统在价值链中的定位

政府服务依赖各部门所掌握的数据，而这些数据之间很少能够达成一致。**政务数据共享交换平台**（government data sharing & exchange platform）是一个跨部门的横向系统，仅在获得授权时在部门之间传输数据，并使每一次流转均可归因。

它是底座，而非面向公众的入口。面向公众的门户（一网通办，同级的 `one-stop-service` 方案包）是使用部门之一，内部审批系统、信用系统和分析系统亦然：

```
  提供部门                                 使用部门
  --------------------                     ---------------------
  公安局（人口信息）                       市场监管局 / 医保 / 人社 / 税务
  市场监管局（法人单位） ┌────────┐        一网通办门户（面向公众）
  自然资源（地理空间） ───────▶│共享交换│◀────── 分析与决策支持
  人社 / 医保           ───────▶│平台    │        公共数据开放门户（开放数据）
  电子证照库            ───────▶│        │
                            └────────┘
                                 │
                      目录 · 授权 · 血缘 · 质量
                      分类分级 · 脱敏 · 审计
```

核心难题是**经授权且可追溯的共享**：任何数据传输都必须有一项已记录且可撤销的共享授权，每次共享均须可归因（`AGENTS.md`）。一个平台若在技术上完成了数据传输，却未记录原因，无论吞吐量多高，都未满足其核心要求。

## 2. 指导原则：默认共享

《政务信息资源共享管理暂行办法》（国发〔2016〕51号）确立了本领域的根本规则：

> 以共享为原则，不共享为例外；需求导向、无偿使用；统一标准、统筹建设；
> 建立机制、保障安全。

由此产生两项操作性影响，并塑造其他所有内容：

1. **共享是默认状态；不予共享是必须论证的例外。** 同一部办法第十条规定，被归类为**不予共享**（not shareable）的资源必须具备**法律、法规或中共中央/国务院政策依据**。因此，“不予共享”是一项负有引证义务的结论，而非一种偏好。
2. **政务部门之间的共享无偿。** 商业数据交换的商业模式完全不适用。

## 3. 三种共享类型——本方案包的核心分类

《办法》第九条将政务信息资源划分为三种共享类型：

| 共享类型 | 中文 | 定义（依据第九条） | 平台影响 |
|---|---|---|---|
| **无条件** | 无条件共享 | 可供**所有**政务部门使用 | 无需针对各使用部门逐一取得共享授权；仍须记录 |
| **有条件** | 有条件共享 | 可供**相关**部门使用，或仅共享一部分 | 需要审批工作流和共享授权 |
| **不予共享** | 不予共享 | 不适合共享 | 必须引用法律、法规或政策依据（第十条） |

> ⚠️ ASSUMPTION: 本方案包将共享类型视为**目录项的属性**，用于驱动工作流行为，而非自由文本标签。这是本方案包的设计立场；第九条定义了这些类型，但未定义系统实现。

同一部办法第十条还列出了**基础信息资源**——人口信息、法人单位、自然资源和空间地理信息、电子证照——其**基础信息项**必须无条件共享。这些资源通常数据量大、敏感度高，构成平台往往最先建设的骨干。

## 4. 核心流程（L1 视图）

1. **登记**——提供部门在政务信息资源目录中登记一项数据资源，并附具元数据、共享类型、分类分级和所有者。
2. **申请**——使用部门提出访问申请，声明使用用途、范围和期限（第十四条：使用仅限于所声明的使用用途）。
3. **审批**——对于有条件资源，由提供部门（在政策要求时还包括平台主管机构）批准，并记录共享授权。
4. **交换**——数据通过交换通道流转：库表、文件或 API（接口）。调度、批处理和增量交换均适用。
5. **使用与记录**——使用部门在声明的使用用途内使用数据；使用情况会被记录。
6. **监控与一致性核对**——监控质量、时效性，以及提供部门持有的内容与实际交付内容之间的一致性（第十三条：提供部门必须确保共享数据与其所持数据一致）。
7. **撤销授权与审查**——共享授权到期或被撤销；全程使用情况均可审计。

## 5. 为何这一系统尤其难以正确实现

- **闭环必须闭合。** 授权 → 审批 → 共享 → 血缘是一个*循环*，而不是一个顺序（`AGENTS.md`）。一项从不撤销的授权、一项没有共享授权的共享，或一条止步于“调用了某个 API”的血缘，都会破坏闭环。
- **不予共享需要引证。** 第十条意味着，平台必须能够存储并展示针对“不予共享”分类的*不予共享依据*。一个不含来源字段的下拉框无法满足这一要求。
- **目录是根对象。** 它将提供部门、资源、分类分级和使用部门关联起来（`AGENTS.md`）。没有目录，就没有可供授权对应的对象。
- **分类分级必须驱动强制执行。** 分类分级决定脱敏规则和访问规则；如果分类分级只是用于报告的元数据，而不是用于执行的政策，那么这种控制就不存在。
- **跨部门权责具有政治性，而非技术性。** “谁经手，谁使用，谁管理，谁负责”（第十四条）以一种任何系统都无法单独落实的方式分配责任；平台只能使责任*可见并得到强制执行*。
- **开放数据适用不同规则。** 面向公众发布不等同于与另一个部门共享：元数据模型（DCAT）、同意依据和脱敏门槛均不相同。

## 6. 质量指标定义

L1 界定意图；阈值在 L2 成为 NFR 目标。

| 指标 | 回答的问题 |
|---|---|
| 目录覆盖率与时效 | 目录能否可靠呈现现有资源情况 |
| 共享授权完整率（具有有效且未过期共享授权的共享占比） | “无授权不得传输”规则是否得到遵守 |
| 交换成功率与时延（按通道） | 底层传输链路是否正常工作 |
| 一致性核对差异（提供部门与使用部门） | 交付数据是否与源数据一致 |
| 撤销授权提前量（发起请求 → 实际移除访问权限） | 撤销授权是否真正生效 |
| 使用用途符合率（符合已声明使用用途的使用占比） | 第十四条的要求是否具备可观测性 |
| 脱敏通过率 | 分类分级驱动的脱敏是否有效 |
| 开放数据发布时效 | 开放数据前端是否得到维护 |
