# 00-context / 利益相关方

## 1. 组织

| 组织 | 职责 | 系统关系 |
|---|---|---|
| **平台管理/主管部门** | 拥有平台、目录标准和跨部门政策 | 运营并治理平台 |
| **提供部门** | 登记资源、发布元数据、保持数据新鲜且一致、审批访问 | 上游；“谁主管，谁提供，谁负责”（国发〔2016〕51号 第十三条） |
| **使用部门** | 声明使用用途并申请访问，仅将该数据用于所声明的用途 | 下游；“谁经手，谁使用，谁管理，谁负责”（第十四条） |
| **基础信息资源库牵头部门**（人口/法人/地理/电子证照） | 建设并维护基础信息资源库 | 价值最高的提供部门；基础信息项可无条件共享 |
| **目录管理办公室**（目录管理） | 汇编并维护政务信息资源目录，监督其时效 | 拥有根对象 |
| **网信/安全主管部门** | 网络安全等级保护定级、安全审查、事件响应 | 设定控制要求；开展审计 |
| **个人信息保护** | 个人信息保护法（PIPL）义务、同意依据、删除请求 | 使用分类分级结果；驱动删除处理 |
| **公共数据开放办公室**（公共数据开放） | 公共数据集发布、开放数据门户内容 | 同一平台的使用方，但适用不同规则 |
| **一网通办运营方** | 面向公众的服务，使用共享数据 | 通过已发布接口的使用方（`AGENTS.md`） |
| **法制/政策** | “不予共享”和有条件共享的法律依据 | 提供平台必须能够存储的引证 |
| **内部审计/监督** | 控制执行和合法使用的证据 | 授权、日志和血缘的只读使用方 |

## 2. 角色（应用参与者）

| 角色（英文） | 中文 | 关键权限/任务 |
|---|---|---|
| Resource registrar（提供部门侧） | 资源登记人 | 登记资源，声明共享类型、分类等级和负责人 |
| Resource owner | 资源负责人 | 对一项资源的元数据、时效性和质量负责 |
| Access requester | 访问申请人 | 申请访问，说明使用用途、范围和期限 |
| Access approver | 审批人 | 批准/拒绝有条件访问请求；在获授权限范围内审批 |
| Grant administrator | 授权管理员 | 签发、修订、暂停和撤销授权 |
| Catalog editor | 目录编辑 | 在本部门内维护目录项和元数据 |
| Catalog supervisor | 目录审核/管理者 | 审核并发布目录项；执行目录标准 |
| Exchange channel operator | 交换运维 | 运维库表/文件/接口交换通道、调度计划和重试 |
| Classification officer | 分类分级专员 | 指定并复核分类等级；推动脱敏策略制定 |
| Masking/policy administrator | 脱敏策略管理员 | 按分类类别定义脱敏规则 |
| Usage auditor | 使用审计员 | 只读审查授权、使用日志和血缘 |
| Open-data publisher | 开放数据发布者 | 使用 DCAT 元数据将数据集发布到开放数据门户 |
| Platform operator | 平台运维 | 运行平台及其组件；**无权**决定业务规则 |

### 非人类参与者

| 参与者 | 说明 |
|---|---|
| **目录服务** | 连接提供部门、资源、分类分级和使用部门的根对象（`AGENTS.md`） |
| **授权引擎** | 根据授权判定传输是否可以进行 |
| **交换通道** | 库表 / 文件 / 接口适配器；各自具有不同的失败语义 |
| **调度器** | 批处理、增量交换窗口、重试 |
| **血缘记录器** | 来源 → 授权 → 使用部门 → 交付物 |
| **质量/一致性核对作业** | 比对提供部门持有的内容与交付给使用部门的内容 |
| **脱敏引擎** | 在交换时应用分类分级驱动的脱敏 |
| **审计日志存储** | 授权、传输和使用情况的只追加记录 |
| **身份提供方** | 对部门用户进行身份认证；提供组织/部门声明项 |
| **印章/签名服务** | 用于签署协议或审批记录 |

## 3. 外部/上游-下游系统作为参与者

- **部门业务系统** — 源数据的真正所有者。
- **基础信息资源库** — 人口、法人、地理空间、
  电子证照。
- **身份提供方 / 政务统一身份认证** — 身份认证和组织属性。
- **一网通办服务门户** — 通过已发布接口接入的使用方。
- **信用/社会治理系统** — 受监管数据的使用方。
- **公共数据开放门户** — 开放数据前端。
- **网络安全等级保护（MLPS）安全管理平台** — 等级保护报告与
  监控。
- **保密/密码管理设施** — 涉密数据纳入范围时使用的设施。
- **监督与审计系统** — 证据的外部接收方。

## 4. 参与者目标（主要）

- **提供部门**：发布一次、保持控制，且不因使用部门误用数据而受到追责——责任边界应清晰可见，而不是事后争论。
- **使用部门**：在可用时间内获取数据，并清楚了解可以如何使用这些数据——同时*停止*向市民重复收集平台本可提供的信息。
- **审批人**：请求内容明确无歧义，且附有声明的使用用途，使审批成为有据可依的行为，而不是走形式。
- **目录管理办公室**：目录足够及时，能够作为现有资源可信的地图。
- **审计人员**：针对任何传输，重建哪项授权准许了传输、使用部门声明了什么，以及实际流转了哪些数据。
- **安全主管部门**：证明实施了分类分级驱动的管控，而不是仅将分类分级作为文档说明。
- **市民（间接受益者）**：无需被要求重复提交同一份文件。

> ⚠️ ASSUMPTION: 本方案包假定责任边界遵循第一张表中引用的两项
> 《办法》原则。这些原则虽有引证依据，但**平台如何对其进行编码**
> （例如，使用部门声明的使用用途是否可由机器校验）属于本方案包的
> 设计问题，L1 未作规定。
