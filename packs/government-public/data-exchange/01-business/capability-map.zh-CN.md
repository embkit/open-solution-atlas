## 1. L1 能力

| # | 能力 | 必须回答的问题 | 说明 / L1 定位 |
|---|---|---|---|
| **CAP-01** | **目录与资源登记** | 存在哪些资源、由谁所有，以及可按何种条件共享 | 连接提供部门、资源、分类分级和使用部门的根对象（`AGENTS.md`） |
| **CAP-02** | **授权与授权生命周期** | 是否允许进行传输，以及能否停止传输 | 申请 → 使用用途 → 审批 → 授权 → 撤销；授权在设计上可撤销 |
| **CAP-03** | **交换通道** | 数据在物理层面如何流转 | 库表/文件/接口；三者是否均为一等能力仍是一个尚待确定的问题（`README.md` #1） |
| **CAP-04** | **分类分级与脱敏** | 适用何种保护措施，以及在何处强制执行 | 分级驱动规则，在交换时强制执行 |
| **CAP-05** | **血缘与归因** | 对于任何传输，谁授权、为何授权以及传输了什么 | 可审计闭环的后半部分 |
| **CAP-06** | **质量与一致性核对** | 交付的数据是否与提供部门持有的数据一致 | 第十三条将此定为提供部门的义务 |
| **CAP-07** | **使用监控与审计** | 使用部门是否始终遵守其声明的使用用途 | 第十四条将按用途使用定为义务 |
| **CAP-08** | **开放数据发布** | 如何生成和描述开放数据集 | 采用 DCAT 建模；属于不同的规则体系，不是其子集 |
| **CAP-09** | **身份、组织与部门上下文** | 谁在行事，以及代表谁行事 | 部门身份、角色、委派、服务账号 |
| **CAP-10** | **运营与安全合规** | 平台自身是否受到管控并保持可用 | 等保控制措施、事件响应、容量 |

## 2. 边界（各项能力*不*负责什么）

| 能力 | 明确**不**属于其职责范围 |
|---|---|
| 01 目录 | 决定某项共享是否获批——这属于 02 |
| 02 授权 | 决定数据*是什么*——这属于 01 |
| 03 交换 | 决定某次传输是否获准——它执行授权 |
| 04 分类分级 | 决定等级——这属于提供部门和分类分级负责人 |
| 05 血缘 | 使决策具有合法性——它负责记录，以便对决策进行检查 |
| 06 质量 | 修正源数据——它负责报告，由提供部门纠正（第十三条） |
| 07 使用监控 | 裁定滥用行为——它负责呈现，监督方负责裁定 |
| 08 开放数据 | 设定开放依据——它发布已获批准的内容 |
| 09 身份 | 部门权限——它负责识别，不授予权利 |
| 10 运营 | 数据方面的业务策略——它负责运行平台 |

> 此类系统中最常见的失败，
> 是某项能力悄然吸收相邻能力的职责：
> 在 BI 工具而非平台中执行脱敏，把使用用途记录为自由文本备注而非
> 授权属性，或者只在使用部门投诉时才执行一致性核对。上述每项边界
> 都是一项可核验的陈述。

## 4. 全平台范围之外

- 面向公众的服务交付（`one-stop-service` 方案包）——平台通过已发布接口向其提供数据。
- 拥有源数据的业务系统。
- 基于共享数据构建的分析/BI（`data-ai` 方案包）。
- 政务云和网络基础设施——承载平台运行的基础环境。
- 组织的数据治理**策略**——平台执行决策，而不制定决策。
