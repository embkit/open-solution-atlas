# 00-context / 行业简报——一站式政务服务平台（一网通办）

## 1. 本系统在价值链中的定位

公民或企业不应需要先了解自己的问题归哪个部门负责。**一网通办**（一体化在线政务服务）平台负责将一件事——**一件事**——纳入统一、可追踪的线上办理链路，无论需要多少个部门参与办理。

它是面向公众的第一入口。`data-exchange` 同系列方案包是其数据基础；本方案包所对应的系统才是公民和企业实际接触的系统：

```
   政务部门（服务提供方）                    行政相对人（公民与企业）
   ─────────────────────                 ──────────────────────────────────
   服务目录（事项）             ┌──────────────────────────┐
   审批后台             ───────▶│  一体化在线政务服务平台   │
   电子证照 / 电子印章 ───────▶│  （一站式服务）           │
   费用缴纳             ───────▶│                           │
   监管                 ───────▶│  提交 · 跟踪 · 签署       │
   档案                 ───────▶│  缴费 · 好差评             │
                                    └──────────────────────────┘
                                             │  ▲
                                             ▼  │
                    共享数据（人口、证照、信用……）
                    国家统一身份认证（一次认证）
                    电子证照与电子印章共享服务
```

结构性约束载于《国务院关于在线政务服务的若干规定》（国务院令第716号）：除法律另有规定或者涉及国家秘密外，政务服务事项**应当**在一体化平台上办理（第四条）。这并非一项便利化计划——而是一项义务，也正是该平台成为部门数字化政务服务交付根基的原因。

## 2. 目录根：事项（政务服务事项）

本方案包的 `AGENTS.md` 将事项指定为目录根；这是整个系统中最具影响的建模决策。其他几乎一切都由它派生：

```
   事项（政务服务事项）  ── 根对象
   │
   ├── 办事指南：受理条件 · 办事材料 · 办理流程   ← 国令716号 第六条
   ├── 表单                ── 申请人填写的内容
   ├── 办事材料（材料清单）── 必须上传的材料，以及可免于提交的材料
   ├── 审批生命周期        ── 受理 → 审查 → 决定 → 出件
   ├── SLA（办理时限）     ── 限时办结
   ├── 收费项目            ── 如有
   ├── 结果材料            ── 决定书 / 电子证照
   ├── 证照模板            ── 如果结果是证照
   └── 证据与归档          ── 电子文件归档
```

由于第六条要求办事指南声明受理条件、办事材料、办理流程，事项并非目录中的一个标签，而是驱动表单生成、材料要求、路由和时限的单元。如果平台将事项建模为一个对象、将表单建模为另一个对象，两者就会逐渐偏离并相互矛盾。

## 3. 确立平台价值的条款

第七条正是确立一网通办目的的条款：

> 政务服务机构通过数据共享能够获得的信息，不得要求行政相对人另行提供。

**机构已经能够通过数据共享获得的信息，不得再次要求申请人提供。**

> 这是防止重复提交规则，是系统必须满足的硬性约束，而非服务愿景。这意味着，表单字段的设置不是界面设计问题：凡是重复采集共享数据源中已有信息的字段，只要被设为*必填*，就构成合规缺陷。`data-exchange` 方案包使这条规则能够落实；本方案包则必须确保例外情形可以审计，而不是在无说明的情况下悄然处理。

## 4. 核心流程（L1 视角）

1. **查找**——申请人搜索目录并阅读已发布的办事指南（第六条：办事指南**应当**发布在平台上）。
2. **一次认证**——通过国家统一身份认证系统实现一次认证、全网通办（第五条）。
3. **数据预填 / 共享数据核验**——通过共享取得的数据用于数据预填和核验，而不是要求申请人另行提供（第七条）。跨部门调用须征得同意并进行审计（`AGENTS.md`）。
4. **提交**——提交表单、办事材料和同意声明；创建办件实例并进行跟踪。
5. **受理或一次性告知**——机构要么予以受理，要么作出一次性告知，一次性列明所有缺失内容，而不是零散地予以驳回。
6. **审查 / 决定**——审批生命周期在限时办结的时限内运行至作出决定。
7. **出件与签署**——结果予以出件；加盖电子印章，并在结果为证照时生成电子证照（第九条/第十条）。
8. **缴费**——在适用的情况下缴纳行政收费。
9. **评价**——好差评反馈形成闭环。
10. **归档**——电子文件以电子形式归档（第十二条）。

## 5. 本系统为何尤其难以做好

- **目录是面向公众的合同。** 办事指南一经发布，申请人就有权据此行事。平台若悄然更改受理条件，不仅是不一致，而且属于违法行为。
- **“一件事”是组合体，而非复制品。** 一件事横跨多个部门，每个部门都有各自的法律依据、各自的决定和各自的责任。平台必须呈现一段统一的办理旅程，同时不抹去每项决定的责任归属。
- **防止重复提交的规则会与平台自身的便利逻辑相冲突。** 要求申请人提供文件很容易；证明该文件已经可以获取却很难。默认要求申请人提供材料的平台看起来更友好，却不合规。
- **电子成果具有法定效力。** 电子印章和电子证照与纸质印章和纸质证照具有同等法律效力（第九条/第十条），电子档案亦然（第十二条）。完整性、签署和归档由此不再只是工程偏好。
- **依赖项均为全国性外部系统。** 统一身份认证、国家统一电子印章系统和电子证照共享服务系统是**平台，而非功能**（`AGENTS.md`）：本方案包必须依据其已发布标准与这些系统集成，绝不得重新实现。重新实现印章或身份认证既不合规，也会带来安全责任。
- **旧有流程必须在迁移后继续运行。** 国发〔2022〕5号将整合与数据共享设为项目审批和验收的条件，因此真正的难题通常是新旧共存，而不是从零建设。
- **线下和协助办理渠道仍然存在。** 将老年人、残障人士和偏远地区人群排除在外，是平台明确要求避免的失败模式；这约束的是渠道策略，而不只是用户界面。

## 6. 定义质量指标

L1 界定意图；在 L2，阈值将成为 NFR 目标。

| 指标 | 回答的问题 |
|---|---|
| 材料净减少量（每个事项要求提交的材料数与基线相比） | 防止重复提交规则是否真正发挥作用 |
| 一次性告知率及完整性 | 是否一次性告知申请人全部缺失内容 |
| 各事项、各部门的限时办结率 | 是否达到承诺的办结时限 |
| 全流程网上办理率 | 平台是否是实际办理渠道，而非线下办理的前台 |
| 重新提交率（补正次数） | 办事指南在首次提交时是否准确 |
| 跨部门调用时延及同意覆盖率 | 共享数据核验是否快速且合法 |
| 归档完整性（电子形式，依据第十二条） | 记录是否按规定形式留存 |
| 好差评分布及响应情况 | 反馈是否真正带来改变 |

## 7. 支撑模型的公开材料

**行政法规（按条款引用）：**

- **《国务院关于在线政务服务的若干规定》**（国务院令第716号，2019-04-26 公布，自公布之日起施行）——平台设立的根本义务。引用条款：第四条（事项纳入一体化平台）、第五条（统一身份认证/一次认证）、第六条（办事指南三项要素）、**第七条（不得重复要求提供可共享获取的信息）**、第九条（统一电子印章系统/同等效力）、第十条（电子证照共享服务系统/同等效力）、第十一条（可作为办理依据）、第十二条（电子文件归档/电子档案同等效力）、第十五条（电子签名/印章/证照/档案的定义）。官方文本：司法部国家行政法规库 https://xzfg.moj.gov.cn/front/law/detail?LawID=445；国务院公报 https://www.gov.cn/gongbao/content/2019/content_5389312.htm
- **《国务院关于加快推进政务服务标准化规范化便利化的指导意见》**（国发〔2022〕5号）——要求能够使用全国一体化在线政务服务平台的部门停止建设单独系统，并将整合与数据共享设为项目审批和验收的条件；同时要求由省级层面协调地方平台。

**电子证照标准（已核验：2018-11-15 发布，2019-01-01 实施，现行有效，归口国家密码局）：**

- **GB/T 36901-2018《电子证照 总体技术架构》**
- **GB/T 36902-2018《电子证照 目录信息规范》**
- **GB/T 36903-2018《电子证照 元数据规范》**
- **GB/T 36904-2018《电子证照 标识规范》**
- **GB/T 36905-2018《电子证照 文件技术要求》**
- **GB/T 36906-2018《电子证照 共享服务接口规范》**

这六项均为**集成接口**，这正是 `AGENTS.md` 所要求的：电子证照能力应予接入使用，绝不重新构建。

**其他适用规范（此处仅列明名称；条款映射在 L2 阶段完成）：**

- **GB/T 22239-2019**《网络安全等级保护基本要求》——等级保护基线；三级是此类平台的通常假设（`README.md`）。
- **《中华人民共和国网络安全法》**（2017-06-01 施行）· **《数据安全法》**（2021-09-01 施行）· **《个人信息保护法》**（2021-11-01 施行）。

> ⚠️ ASSUMPTION: 等保**三级**是本方案包针对此类平台所声明的工作假设，正如 `README.md` 中所记录的。它**并非**引用依据，也未进行定级；实际等级由外部确定，各部署必须采用自身的等级认定。
>
> ⚠️ ASSUMPTION: GB/T 36903/36904（元数据和标识符规范）**仅**约束国家电子证照服务**内部**的电子证照模型。平台自身的内部事项模型不会自动成为 GB/T 36903 目录。是否在内部与该标准保持一致，是 L2 阶段的决策。
