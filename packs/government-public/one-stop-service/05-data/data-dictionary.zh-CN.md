# 05 · 数据字典

> 仅包含核心实体。字段语义具有规范性；类型仅供说明。
>
> ⚠️ ASSUMPTION — 字段级设计属于方案包设计。`02-requirements/compliance.md` 中所列法规文件仅用于指称；本文不引用具体条款，也不声称符合相关要求。

## SERVICE_ITEM / GUIDE_VERSION

| 字段 | 语义 |
|---|---|
| `SERVICE_ITEM.kind` | 仅允许两个值（约束 1，ADR-0001）。该类型并非标签：它决定结果产物，只有行政权力事项才会生成决定书，并产生行政复议和诉讼方面的后果 |
| `GUIDE_VERSION.acceptance_conditions[]`, `materials[]`, `process_steps[]` | 发布时三者均为 NOT NULL（约束 2，ADR-0002）。由于办事指南**就是**已公布的合同，申请人有权依据其办理——因此每次变更均须标注日期并明确变更责任人，而提交申请时所依据的版本则记录在办件中 |
| `GUIDE_VERSION` immutability | 一经发布即不可变。对已发布指南进行在线编辑，意味着每一项历史办件都是依据一个现已不存在的指南提交的，“我当时有权依据什么办理？”将无法回答 |

## APPLICATION / STATUTORY_STEP / CLOCK_EVENT

| 字段 | 语义 |
|---|---|
| `STATUTORY_STEP.kind` | 受理 / 审查 / 决定 / 出件（约束 3，ADR-0006）。这些是**法律定义的行为**，而非工作流状态；将“已受理”和“已批准”归为同一个词，恰恰会使办结时限的含义随之丧失 |
| `CLOCK_EVENT` 中种类为 `start` 的事件 | 在**受理时**写入（约束 4，BR-09）。这是方案包的设计立场，而非条文引用——同时也是一项存储约束，因为歧义正是朝“更有利”的方向消解：从提交开始计时，而义务从受理起算，会让所有报告数字都显得更好 |
| `ONCE_NOTICE.missing_items[]` | 必须完整（约束 5，BR-07）。一次性告知发生在**受理之前**；补正发生在**受理之后**。将二者混同，会使平台最终反复驳回申请人，而不是一次性告知 |
| `SUPPLEMENT.accepted_before` | NOT NULL（约束 5）。若此前未予受理而要求补正，该请求实际上就是未被称作一次性告知的一次性告知 |

## FIELD_CLASSIFICATION / SHARED_LOOKUP / PERMITTED_ALTERNATIVE

| 字段 | 语义 |
|---|---|
| `FIELD_CLASSIFICATION.obtainable_by_sharing` | 按**字段**设置且均为 NOT NULL（约束 6，ADR-0005）。如果按整张表单分类，就会漏掉本不应索取的单个字段——而该规则只会逐个字段地失效，这已是它唯一可能的失效层级 |
| `SHARED_LOOKUP.outcome` | `prefilled`、`verified` 或 `failed`。**`failed` 必须对应一个 `PERMITTED_ALTERNATIVE`**（约束 7）：回退方案本身*就是*控制措施，而一个无人定义的回退方案，正会让规则悄然变成“要求提供” |
| 该机制防止的失败 | 要求提供文件很容易；证明文件已经能够获取却很难。平台惯有的做法——默认要求申请人提供——看似更友好，却不合规 |
| `FIELD_EXEMPTION.reason` | NOT NULL（约束 8）。未经说明的豁免会使该规则从必须满足的属性蜕变为一种偏好 |

## DATA_CALL / CONSENT_STATE

| 字段 | 语义 |
|---|---|
| `consent_state_ref` | NOT NULL，且该状态必须允许此用途（约束 9，BR-08）。没有记录依据的调用既是合规缺陷，同时也是平台过度收集信息的证据 |
| `CALL_PURPOSE` 版本管理 | 用途发生变化，即形成该用途的新版本。目前正在使用、却从未取得同意的用途，正是 CTL-07 所指出的用途累积失败 |

## SEAL_APPLICATION / STATUS_CHECK

| 字段 | 语义 |
|---|---|
| `seal_id` | 解析至国家统一电子印章系统（约束 10，ADR-0007）。本地生成的印章会成为需要额外保障和对账的第二枚印章，而且其有效性无法对照证书进行核验 |
| `valid_at_ts` | NOT NULL，且**绝不可由状态检查覆盖**。该字段用于区分两类截然不同的文档：签署时有效、此后被作废，意味着当时已正确用印；签署时无效，则意味着从未正确用印，无论该印章当前状态多么良好 |
| `STATUS_CHECK` | 一项应予**调用**的服务（《措施》第 17 条），而非自行实现的服务。其结果单独记录，绝不替代 `valid_at_ts` |
| 证书绑定 | 印章的有效期不得超过其证书的有效期（第 16 条）——因此，必须在文档签署前明示印章到期情况 |

## CHANNEL_DECLARATION

| 字段 | 语义 |
|---|---|
| 五个方面 | 启用前五项均为 NOT NULL（约束 11，ADR-0004）：输入、支付路径、身份处理、服务履行来源、展示 |
| `identity_model` | 必须采用国家服务（约束 11，BR-03）。**这是最难满足的方面**：在本地进行身份认证的渠道就等于取得了公民身份，而 `AGENTS.md` 明确禁止这样做——而 POS 或辅助销售通常会将其列为“临时”例外 |

## ELECTRONIC_FILE / ARCHIVE_RECORD

| 字段 | 语义 |
|---|---|
| `verified` 和 `retrievable` | 两者均为 NOT NULL 且为真（约束 12，ADR-0008）。**附加到文档管理系统并不等于归档。**第 12 条规定电子档案与纸质档案具有同等法律效力，而完整性声明不能以此为依据 |
| 由此产生的约束 | 平台的**办件数据模型就是归档对象**。模型遗漏的字段对应一条不会形成的记录，而迁移中删除某一字段属于归档缺口，而非数据模式变更 |

## RETENTION_CLASS

| 字段 | 语义 |
|---|---|
| `declared_window` | 每个类别均为 NOT NULL（约束 13）。办件、文档、印章和日志具有不同的性质和保留义务；BR-12 禁止设置全局记录行 |
| 取值 | **本方案包未规定具体取值。** |

> ⚠️ ASSUMPTION — 此处每项字段语义均属于方案包设计。编写期间，已依据官方文本核验国令第716号第 4、5、6、7、9、10、11、12 和 15 条，以及国办发〔2025〕33号第 5、16、17、21、22、23 和 27 条；根据本仓库的范围决定，**不进行时效性跟踪**，且不声称符合相关要求。
