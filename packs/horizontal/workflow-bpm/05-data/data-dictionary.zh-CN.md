# 05 · 数据字典

> 仅包含核心实体。字段语义具有规范性；类型仅供参考。
>
> ⚠️ ASSUMPTION — 字段级设计属于本方案包的设计范围。BPMN 2.0 提供词汇；
> 不主张符合 BPMN 2.0。

## DEFINITION_VERSION

| 字段 | 语义 |
|---|---|
| `version` | 发布后即不可变（BR-02，与约束 5 相邻）。流程定义的变更即为一个新版本；流程实例的审计轨迹记录“依据当时生效的版本”，而如果版本可以变动，这一陈述就不成立 |
| `in_flight_treatment` | NOT NULL（约束 2）：`finish_on_old`、`migrate` 或 `terminate`。**默认值为引擎碰巧采用的那一种**，因此不能将其留作隐式设置 |
| `impact_statement_ref` | NOT NULL。发布时若不知道哪些正在运行的流程实例会受到影响，就会导致用户自行发现其后果（NFR-010） |

## INSTANCE_EVENT

| 字段 | 语义 |
|---|---|
| `kind` / `actor` / `ts` / `reason` | 每次转换都追加一条记录，且四个字段均须具备（约束 5，NFR-001）。缺少操作者或缺少原因的状态变更无法解释 |
| `rule_id` | 网关、定时器和规则驱动的决策均须填写此字段。正是它使记录能够回答“为什么会路由到那里？” |
| `definition_version_id` | 每个事件均须填写此字段，从而能够依据产生该事件的版本解释审计轨迹 |
| 不可变性 | 不授予 UPDATE 或 DELETE 权限。更正应记录为由具名授权人发起的**补偿事件**（BR-10）。此字段集即 ADR-0005 的全部内容：事件即状态，状态即为 `fold(events)`——可逐位重放，绝不以可变字段为依据进行验证 |

## WORK_ITEM / COMPLETION_POLICY

| 字段 | 语义 |
|---|---|
| `pattern` | 限定为已定义的词汇表（约束 6）：assign（指派/分发）、claim（签收/认领）、transfer（转办）、delegate（代办/委托）、会签、或签、加签、退回、撤回、add-comment（加签意见/批注）。集合之外的操作都是毫无语义的臆造行为——这正是本方案包旨在防止的失败 |
| `COMPLETION_POLICY.variant` | 会签使用 `unanimous` 或 `all-responded`；或签使用 `cancel_others` 或 `never_surface`。多参与者模式**必须**填写此值（约束 7）。BPMN 2.0 既未提供该术语，也未提供该策略 |
| `expires_ts` | 工作项对流程实例进度所持有的约束。既无到期时间又无所有者的工作项会使流程实例停滞，且无人对此负责 |

## PARTICIPANT / ROLE / DELEGATION

| 字段 | 语义 |
|---|---|
| 约束 8 | 任何 `DEFINITION` 行均不得包含用户引用。用户引用通过 `ROLE` 和 `scope_ref` 解析。流程定义中的用户名就是集成版的硬编码，而且其失败方式恰恰如此：有人调岗时悄无声息地失效 |
| `DELEGATION.scope` | NOT NULL 且**结构化**（约束 8）。以自由文本记录的范围等于不受任何约束的范围；有界委托正是在这种情况下变成一种被记录为临时便利的永久权限转移 |
| `valid_to` / `revoked_ts` | 两者均须填写。无界委托是非法的——正是这两个字段使“有界”成为结构性约束，而非仅仅是一种愿望 |

## DOCUMENT / SEAL_REF

| 字段 | 语义 |
|---|---|
| `authority_ref` | NOT NULL（约束 9）：签发者、依据、时间戳。决策文档若没有可归责的签发者、依据和时间戳，就无法进行抗辩 |
| `SEAL_REF.valid_at_ts` | **签署时**的有效性，而不是当前有效性（CTL-04）。这一区别确实存在：后来失效的印章不会追溯性地使一份妥善盖章的文档失效；而使用已经过期的印章所盖的文件从来就不是有效的 |
| 印章机制 | ⚠️ 未作规定。本方案包要求进行有效性校验和归属判定，但不选择密码学原语或提供商——这是部署时的选择 |

## CN VARIANT 实体

| 字段 | 语义 |
|---|---|
| 约束 11 | `OFFICIAL_DOCUMENT`、`DOCUMENT_NUMBER` 和 `SEAL_REF` **只能由中国变体写入**（BR-11）。FR-028 要求仅含核心功能的部署在这些实体缺失时仍能运行，由此以实际运行证明隔离，而不是仅作声明 |
| `DOCUMENT_NUMBER.value` | 从有界的外部资源中分配。分配必须无缺口且可审计——缺口是资源核算中的缺陷，而不是表面问题 |
| 边界侵蚀 | 这类陷阱总是朝这个方向发展：核心对变体形成一项“小”依赖——一个状态名称、一个枚举或一套标识符方案。约束 11 正是为此而设 |

## RETENTION_CLASS

| 字段 | 语义 |
|---|---|
| `declared_window` | 每类均为 NOT NULL（约束 10）。流程实例、文档、印章和日志的性质与义务各不相同，因此 BR-09 禁止使用全局行 |
| 值 | **本方案包未规定任何具体值。** |

> ⚠️ ASSUMPTION — 此处每项字段语义均属于本方案包的设计范围。`03-domain/glossary.md` §2 中的审批词汇定义是本方案包的**贡献**，并标注为 `[PACK]`：BPMN 2.0 未定义其中任何术语，因此与厂商语义发生冲突时，即是在与本方案包发生冲突；
> FR-013/FR-014 要求对策略作出*声明*，而不是予以假定。
