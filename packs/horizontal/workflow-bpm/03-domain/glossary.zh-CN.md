# 03-domain / 术语表

> **本文件在 L1 阶段的用途。** 本方案包的 `AGENTS.md` 要求将中文
> 审批术语*明确定义*，而不是仅用作标签，
> 因为 BPMN 2.0 并未定义其中任何一个。本术语表用于陈述这些语义。
> 本文档在此定义的术语在整个方案包中均仅采用一种含义；后续不会引入同义词。
>
> `Source` 列记录依据：**[BPMN]** OMG 表示法（已引用），
> **[PACK]** 本方案包贡献的定义，因为没有公共标准
> 对其作出规定，**[STAT]** 法规，**[ENG]** 引擎中常见但尚未标准化的
> 约定。任何未标记 `[PACK]` 且未注明引用的内容均属假设，必须明确说明。

## 1. 核心流程对象

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Process definition** | 流程定义 | 经版本化并发布的制品，描述某一流程的实例如何推进。它并非运行中的对象。 | [PACK] |
| **Process instance** | 流程实例 | 流程定义的一次执行，拥有各自的数据、身份和历史记录。 | [BPMN] |
| **Token** | 令牌 | 实例控制流中位置的抽象标记。此处用于推理语义；不一定是实现选择。 | [BPMN] |
| **Activity** | 活动 | 流程中的工作单元：任务、子流程、调用活动。 | [BPMN] |
| **Task** | 任务/待办 | 分配给参与者的工作项。不同于 BPMN *user task*——此处，“task”是通用概念，而“user task”是由人执行的那一类。 | [PACK] |
| **Gateway** | 网关 | 流程分支或合并的节点：排他、包容、并行、基于事件、复杂。 | [BPMN] |
| **Event** | 事件 | 在某一时点发生的事情：开始、中间（消息/定时/信号/错误）、结束。 | [BPMN] |
| **Sub-process** | 子流程 | 本身即流程的活动，可为嵌入式（共享父作用域）或可复用（独立）。 | [BPMN] |
| **Lane / participant** | 泳道/参与者 | 按组织角色或系统对流程进行的分区。 | [BPMN] |
| **Multi-instance activity** | 多实例活动 | 针对一组参与者或项目重复执行的活动，并带有完成条件。 | [BPMN] |

## 2. 任务术语——BPMN 未定义的术语

以下六项正是每套中国 OA 部署都会用到、而每家厂商的定义又各不相同的术语。**每项均在此依据任务的状态机加以定义，以确保规范含义明确。**

| 术语（英） | 中文 | 定义（状态机层面） | 来源 |
|---|---|---|---|
| **Assign** | 指派/分发 | 任务创建时**即已归属**于特定参与者；它出现在该参与者的收件箱中，未经转办或重新指派，不得由他人认领。 | [PACK] |
| **Claim** | 签收/认领 | 任务创建时**无归属**（提供给某个任务池或群组）；由参与者取得归属。认领后，归属具有排他性。 | [PACK] |
| **Transfer** | 转办 | 参与者**放弃**任务并永久转交他人。原所有者不再持有该任务，此后不得对其执行操作。转办是一项可审计事件，其中列明双方。 | [PACK] |
| **Delegate** | 代办/委托 | 参与者**授予**他人对一项**仍归该参与者所有**的任务执行操作的权利。该授权有明确边界（范围和有效期）。代办人采取的操作既记录在代办人名下，也归因于委托所有者。 | [PACK] |
| **Countersign** | 会签 | 一组参与者必须**全部**对同一工作项执行操作，该工作项才能完成。“全部执行”本身即是一项策略：一致批准与全部响应（有一项拒绝即结束）不同。完成策略有多种；本方案包不预设其中任何一种。 | [PACK] |
| **Or-sign** | 或签 | 工作项在组内**任意一人**执行操作后即完成。其他参与者的任务会被取消，或始终不会变为可操作状态——究竟采用哪一种属于必须明确说明而不能预设的策略。 | [PACK] |
| **Add-sign** | 加签 | 参与者在本人审批之前，将一名额外审批人**插入**正在运行的流程。新增审批人在插入后执行操作，并在原有顺序继续之前完成操作。 | [PACK] |
| **Return for rework** | 退回 | 流程**向后**移至先前的活动或申请人处。存在两种不同语义，绝不可混为一谈：**驳回**（终止实例）与**返工**（退回申请人，可重新提交）。 | [PACK] |
| **Withdraw** | 撤回 | **申请人**在终局决定作出之前撤回实例。仅申请人（或流程所有者）可以撤回，且只能在尚未记录任何有约束力的决定时撤回。 | [PACK] |
| **Add-comment** | 加签意见/批注 | 附加到实例或任务的不具约束力的批注。绝不改变控制流。 | [PACK] |

> ⚠️ ASSUMPTION: 这些术语中的若干项（尤其是会签/或签/加签）在日常使用中
> 非常普遍，但**没有标准定义**——BPMN 中没有，DMN 中也没有。
> 上述定义是本方案包贡献的成果，并已如此标注。需要了解*特定产品*所实现
> 语义的读者必须查阅该产品的文档；本方案包的职责是将语义表述得足够精确，
> 以便据此衡量产品。

## 3. 审批、路由与时间

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Approval condition** | 审批条件 | 判定给定审批人是否必须处理给定实例的谓词（金额、类型、部门、风险）。 | [PACK] |
| **Approval chain** | 审批链 | 实例必须依次经过的审批人有序序列。 | [PACK] |
| **Escalation** | 催办/升级 | 任务超过其计时器所设时限时采取的自动操作：提醒、重新指派或转交上级。触发条件、操作以及授权执行该操作的权限是三个独立决策。 | [PACK] |
| **Business calendar** | 工作日历 | 用于测量 SLA 时长的日历（工作日、节假日、工作时段）。 | [PACK] |
| **SLA / deadline** | 办理时限 | 对实例或任务承诺的完成时限，按工作日历计量。 | [PACK] |
| **Timer event** | 定时事件 | 按计划或经过一定时长后触发的事件；用于驱动提醒、截止期限、自动审批（在允许的情况下）。 | [BPMN] |
| **Auto-approval on timeout** | 超时自动通过 | 计时器到期时的终局自动审批。**争议极大**：只能由明确策略允许，绝不能作为默认设置，因为它会把人工控制转变为默示同意。 | [PACK] |
| **SoD constraint** | 职责分离约束 | 阻止一名参与者同时持有不得组合的两个角色（例如申请人与印章保管人）的规则。该规则来自 IAM 方案包；本方案包对其加以使用。 | [PACK] |

## 4. 文档、公文与记录

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Official document (公文)** | 公文 | 依据组织授权、以规定格式签发并具有机构效力的文档。 | [STAT] |
| **公文 format** | 公文格式 | 公文的版式规则：纸张、构成要素、分页及特定格式。 | [STAT] GB/T 9704-2012 |
| **Electronic 公文 structure** | 电子公文结构 | 电子公文的结构模型——与纸质时代的格式相比，它才是与数字化流程更相关的标准。 | [STAT] GB/T 33476.1-2016（候选） |
| **Document number (文号)** | 发文字号/文号 | 分配给公文的标识符，在其签发机关及序号范围内唯一。编号分配必须无缺口、不可重用且可审计。 | [PACK] |
| **Draft / review / issue (核稿/签发)** | 拟稿/核稿/签发 | 公文签发前的拟稿流转过程：拟稿、正确性审核以及最终签发授权。 | [PACK] |
| **Archive (归档)** | 归档 | 将已完成的记录移交档案主管机构长期保管。 | [PACK] |
| **Retention schedule** | 保管期限 | 一类记录必须保留多长时间，以及到期后如何处置（销毁须经授权）。 | [PACK] |
| **Electronic signature** | 电子签名 | 附加到数据电文上或包含于数据电文中的数据，用于标识签名人并表明签名人认可其内容。 | [STAT] 电子签名法 第二条 |
| **Reliable electronic signature** | 可靠的电子签名 | 其生成数据专属于签名人、签名时由签名人控制，并且能够检测出签名或数据电文此后的更改——因此具有与手写或盖章相同的法律效力。 | [STAT] 电子签名法 第十三条、第十四条 |
| **Data message (数据电文)** | 数据电文 | 通过电子、光学或类似手段生成、发送、接收或存储的信息。 | [STAT] 电子签名法 第二条 |
| **Electronic seal (电子签章)** | 电子签章 | 与签名相对应的机构形式：以电子形式施加的印章。L1 阶段有意不指明标准和提供商。 | [PACK] |
| **Integrity verification** | 完整性校验 | 检测已存储文档或签名是否发生更改的能力——不仅仅是检测其丢失。这是一项法律要求，而不是一项功能。 | [STAT] 电子签名法 第十三条 |

## 5. 审计、重放与运维

| 术语（英） | 中文 | 定义 | 来源 |
|---|---|---|---|
| **Event** | 事件 | 某事件已经发生的不可变记录：类型、操作者、时间戳、实例、载荷引用。 | [PACK] |
| **Audit trail** | 审计轨迹 | 实例所有事件的有序、仅可追加记录。绝不更新，绝不删除，只能由补偿事件取代。 | [PACK] |
| **Replay** | 重放 | 根据事件日志重建实例历史，或重新执行实例。两种不同含义：**重建**（只读，用于审计）和**重新执行**（根据事件重建状态）。本方案包要求前者，并将后者视为一种设计选项。 | [PACK] |
| **Tamper evidence** | 防篡改 | 对审计轨迹的更改能够被检测，而不只是被阻止。审计可以依赖的是这种检测能力。 | [PACK] |
| **Compensating event** | 补偿事件 | 为更正或撤销先前事件而记录的事件。先前事件绝不编辑。 | [BPMN]/[PACK] |
| **Event log export** | 事件日志导出 | 为分析而批量导出审计轨迹。L1 阶段有意不指定交换格式。 | [PACK] |

## 6. 约定

- **"must not" 与 "should"**：本方案包按通常的工程含义使用二者——*must not* 标记违反即构成缺陷的规则。
- **双语术语**：对于中文审批术语（第 2 节），中文术语具有权威性，因为歧义集中于此；对于 BPMN 表示法概念，英文术语具有权威性。
- **不使用同义词**：术语在此定义后，后续章节逐字使用。如果某章需要作不同区分，则定义新术语，而不是扩展现有术语的含义。
