# 00-context / 行业简述 — 工作流、BPM 与办公自动化（OA）

## 1. 该系统在价值链中的位置

几乎没有任何组织会以自由格式电子邮件来运转工作。一旦需要不止少数几个人对步骤顺序、所需证据以及“谁做了什么”的记录达成一致，组织就需要一个**工作流 / BPM 平台**：这是一种横向系统，可将业务流程转化为正在运行、可观测且可审计的流程。

它位于**三个事实来源**与**所有运营系统**之间：

```
   HR / 组织主数据                           业务线系统
   （有哪些人员、向谁汇报）                  （ERP / 财务 / HR / 资产 / CRM）
            │                                     ▲
            ▼                                     │
   ┌─────────────────────────────────────────────┴──────────────────┐
   │  工作流 / BPM 平台                                            │
   │                                                                │
   │  流程定义 ──▶ 流程引擎（实例、任务）                           │
   │  表单定义 ──▶ 表单引擎（数据采集、校验）                       │
   │  规则与网关 ──▶ 决策点（谁必须审批）                           │
   │  文档与记录 ──▶ 内容存储、文号、归档、保留期                    │
   │  事件与审计 ──▶ 谁/何时/什么/结果、重放                        │
   └────────────────────────────────────────────────────────────────┘
            │                                     ▲
            ▼                                     │
   通知 / 消息                              参与者身份（IAM）
   （待办、提醒、催办/升级）                 以及签名/用印身份
```

平台负责**编排**；并不拥有其流转的业务数据。在这样的方案包中，首先应当说明的正是这一边界：一个 OA 平台如果开始“拥有”原本只应由其负责路由的业务逻辑，就会成为第二套 ERP，且无人能够维护。

两个业务域共用同一套基础机制：

| 类别 | 典型工作单元 | 特征 |
|---|---|---|
| **企业 OA / 协同办公** | 审批单——请假、费用报销、采购、合同、用印、公文签发 | 大量规模小、生命周期短、由表单驱动且以人工为主的流程 |
| **业务流程管理** | 端到端流程——订单到收款、理赔处理、事件到解决 | 数量较少、生命周期长、集成密集且系统任务密集 |

本方案包在同一平台上对这两类流程进行建模，因为二者的引擎要求相同；所不同的只是任务的*风格*和合规要求体系。

## 2. 部署原型

| 原型 | 关键特征 |
|---|---|
| **部门级 OA** | 预置的请假、费用和用印表单；从 HR 系统同步组织架构；轻度定制 |
| **企业流程中枢** | OA 表单，以及调用 ERP/财务 API、以 BPMN 建模的跨系统流程；流程层成为集成层 |
| **政府 / 政务 OA** | 上述能力，加上公文处理、文号控制、电子签章、跨部门核验以及记录/归档义务 |
| **嵌入式工作流** | 引擎作为内部能力内嵌于另一产品（ITSM、ERP、低代码平台），而非独立门户 |

> ⚠️ ASSUMPTION: 本方案包将一个逻辑平台建模为服务于全部四种原型，并将政府专用部分（公文/文号/电子签章）视为**部署配置**，而非核心功能。在实际部署中，用印/签名集成几乎肯定会采购，而不是自行构建。

## 3. 核心流程（L1 视角）

1. **起草并提交**——用户填写根据模式构建的表单、附上证据材料并提交；引擎创建一个**流程实例**。
2. **路由与决策**——引擎评估流程定义：是采用顺序分支还是并行分支，以及如何处理网关、多实例会签和委托。每个步骤都会在某人的收件箱中生成一个**任务**。
3. **人工处理**——指派/分发、签收/认领、转办、会签、或签、加签、退回、撤回、代办/委托。计时器用于驱动提醒、办理时限管理和催办/升级。
4. **系统处理**——服务任务调用下游系统、写回结果，或等待回调/消息。
5. **完成并记录**——实例以终局状态结束；审批记录、文档、文号和完整审计轨迹均予以保留，并可检索以供审计。

## 4. 为什么这个系统尤其难以正确实现

- **模型不等于实现。** BPMN 2.0 是一种*表示法与交换*标准；各引擎真正产生差异的是执行语义——令牌流、补偿、多实例完成。两个“BPMN 兼容”引擎对同一张图的运行方式可能不同（见 [`SOURCES.md` §4](../SOURCES.md)）。
- **中文审批术语没有标准定义。** 会签 / 或签 / 加签 / 转办 / 退回 是每套中国 OA 部署中的日常术语，而 BPMN 2.0 未定义其中任何一个。必须明确记录其语义，否则每家厂商都会给出不同定义——而这恰恰是本方案包要防止的问题（见 `03-domain/glossary.md`）。
- **组织架构图始终在变。** 审批取决于汇报关系、岗位和角色，而 HR 每周都会调整这些内容；将审批人硬编码到流程定义中的平台会在无人察觉的情况下失效。
- **可审计性是正确性要求，而不是一项功能。** “每次状态转换都必须可审计、可重放”是本方案包自身的硬性规则（[`AGENTS.md`](../AGENTS.md)）——而仅可追加的审计轨迹正是审批决定在数月后仍能经得起质疑的原因。
- **文档具有法律效力。** 一旦在平台内签发并签署一份公文或合同，平台便开始生成法律制品：完整性、时间戳、保留期和签名有效性便不再是单纯的工程偏好。
- **表单会逐渐失效。** 由模式驱动的表单引擎以部署速度换取一种永久存在的风险：某个校验表达式无人能追溯回某项业务规则。

## 5. 定义质量指标

L1 仅界定意图；阈值和公式将在 L2 固化为规则。

| 指标 | 回答的问题 |
|---|---|
| 实例周期时间（按流程类型，p50/p95） | 一项审批端到端实际需要多长时间 |
| 按时完成率 | SLA/办理时限承诺的达成频率 |
| 任务收件箱时延（签收/认领 → 首次操作） | 瓶颈是人还是引擎 |
| 催办/升级 / 自动提醒有效性 | 计时器是否确实能解除停滞的工作 |
| 流程实例错误率（引擎故障） | 独立于人为延迟的引擎可靠性 |
| 审计完整性 | 拥有完整且责任主体明确的事件记录的状态转换占比 |
| 文档完整性校验率 | 保留文档中哈希仍能通过校验的比例 |

## 6. 支撑模型的公共标准

- **BPMN 2.0.2** (OMG, https://www.omg.org/spec/BPMN/2.0.2/) — 建模词汇：流对象、网关、事件、泳道、工件。本方案包将其流程表示法锚定于此。
- **DMN** (OMG, https://www.omg.org/spec/DMN/) — 决策建模；在 L2 明确审批条件语义后，可作为承载这些语义的候选位置。
- **CMMN** (OMG) — 案例管理；*当前不在范围内*。列出此项是为了表明省略是有意为之，而非疏忽。
- **CMIS 1.1** (OASIS, https://docs.oasis-open.org/cmis/CMIS/v1.1/) — 为文档管理章节背后的文档/内容存储库提供互操作性。
- **IEEE 1849 XES** (IEEE, eXtensible Event Stream) — 若规定对导出日志进行流程挖掘或重放，则可作为候选交换格式；在作出任何一致性声明之前，须确认标准编号（见 `SOURCES.md` §4）。
- **GB/T 22239-2019**《网络安全等级保护基本要求》——平台预期应满足的中国分级保护基线。
- **《中华人民共和国电子签名法》**（2004 年，2015 年和 2019 年修订）——电子签名的法律效力；见 `regulatory-landscape.md`。

> ⚠️ ASSUMPTION: 本方案包有意*不*主张引擎一致性。BPMN 一致性类别是 L2/L3 层的决策；本方案包说明的是其所需的表示法和生命周期语义，而不是某家厂商的一致性概况。
