# ADR-0004 — 审批术语由本方案包定义，因为 BPMN 2.0 未定义这些术语

- 状态：已接受
- 日期：2026-10-12
- 决策人：方案包维护者

## 背景

`AGENTS.md` 指明了本方案包存在的原因：中国审批模式必须定义为明确的语义，而非含义模糊的标签。

会签 / 或签 / 加签 / 转办 / 退回 是每套中国 OA 部署中的日常术语，每家厂商都会对这些术语作出定义。BPMN 2.0 没有定义其中任何一个。这并非 BPMN 的缺口——这些概念不在其作为表示法标准的范围之内——但这意味着，一条写成“当会签组完成时”的需求，在有人把该指称对象写下来之前，是一句无所指的话。

因此，`03-domain/glossary.md` §2 中的每项定义都是本方案包的贡献，标记为 `[PACK]`，本方案包不将这些定义作为引文呈现。

## 备选方案

1. **将术语交由实现方定义**——速度最快，但引用会签的需求无法构建。团队会议会决定其含义，而该决定 nowhere 被记录下来。
2. **采用某家厂商的定义**——指称对象是明确的，但它只属于某一家厂商。更换厂商会改变每项需求的含义，而这种变化在需求文本本身中不可见。
3. **在本方案包中于状态机层面定义这些术语，并将完成策略明确列为待定决策**——指称对象是公开的，歧义情形会被记录为歧义，而不是悄然自行解决。

## 决策

采用方案 3，并将其作为不变量，由 BR-05、FR-009 至 FR-017 和 NFR-007 强制执行：超出既定集合的操作均属非法。

这些定义位于**状态机层面**——归属会如何变化、其他任务会如何处理、哪些操作可逆——因为这些术语的差异正体现在该层面，而实现也可以在该层面接受检验。

有意将两项完成策略留待确定，并如实记录：是否会签因任一拒绝而结束，以及或签是取消其他任务，还是仅仅不呈现这些任务。这些是 L2 层需要作出的决策，而非可以查找的事实。

## 后果

- 正面：引用会签的需求可以实现和测试，部署也可依据公开定义而非某家厂商的定义进行衡量。
- 正面：两项尚未确定的策略会以决策形式清晰呈现，从而避免由最先安装的实现自行确定。
- 负面：这些定义是本方案包的贡献，因此与某家厂商的语义发生冲突，也就是与本方案包发生冲突。FR-013 和 FR-014 要求必须*声明*所用策略，这意味着必须与某家厂商匹配的部署应声明该厂商的变体，而不应因此被视为错误。
- 负面：在状态机层面定义十个术语是一项实实在在的工作，
> 这些定义需要接受与任何其他规范性内容相同的治理。它们并非没有成本。
