# ADR-0003 — 参与者从组织信息源解析，且解析失败时采用安全拒绝策略

- 状态：已接受
- 日期：2026-10-12
- 决策人：方案包维护者

## 背景

审批取决于汇报关系、岗位和角色。在真实组织中，这些关系每周都会发生变化——有人晋升、团队重组、经理在流程执行中途离职。将审批人硬编码到流程定义中的平台会以一种特定方式失效：故障会在生产环境中悄无声息地发生，而且看起来就像“审批不再送达”。

因此，这是一项结构性要求，而非仅供建议：参与者必须**从组织信息源**按角色和业务范围进行解析，绝不能依据流程定义中的用户名来确定。

需要通过 ADR 决定的是故障处理方向。当组织信息源不可用时，平台必须对此作出处理。

## 备选方案

1. **缓存并提供过期的解析结果**——任务会路由给缓存所记录的人员。缓存生成当天这一结果是正确的，但只要有人变更岗位，结果就会立即出错，而这正是该规则意在防止的故障。
2. **回退到已配置的默认值**——任务会路由给备用审批人，审批权便转移到一项无人审核的配置上。路由到“上一任持有者”或“部门负责人”，不过是给硬编码名称换了顶帽子而已。
3. **不进行路由**——任务保持挂起状态，不可用状态清晰可见，待信息源恢复后再解析参与者。

## 决策

采用选项 3，由 BR-04、FR-006、FR-007 和 NFR-005 强制执行，并在 `integration.md` 的故障模式契约中明确规定。

同样的论证也适用于集成版本：提供自有审批人列表的调用方，实际上是在通过 API 硬编码参与者，因此会以相同方式失效。

## 后果

- 正面：审批权限取决于当前组织状况，而非流程定义编写时的组织状况。
- 正面：不可用状态会明确呈现为不可用，而不是表现为看似正确的错误路由工作。
- 负面：组织信息源是关键路径依赖项，任务挂起会造成实际业务影响。本方案包的立场是，这仍是正确的处理方向，因为替代方案会把工作路由给无权处理的人。
- 负面：NFR-005 的失败率包含已挂起的任务，因此较低的失败率既可能表示解析效果良好，也可能表示回退机制从未触发。二者通过 `participant_resolution_failure` 信号加以区分：该信号是挂起路由计数，而不是静默回退计数。
