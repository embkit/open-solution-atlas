# ADR-0002 — 仅追加的执行事件存储作为车间事实的 SSOT

- 状态：已接受
- 日期：2026-10-08
- 决策人：本方案包维护者

## 背景

可追溯性（BR-06）、数据完整性（CTL-02）与 OEE 可信度（BR-09）都要求车间历史
不能被改写。传统的「CRUD + 审计日志」设计让可变行成为权威，而日志只是一份
尽力而为的副本——于是审计依赖日志的完整性，投影（谱系、在制品）也会静默分叉。
可选方案：

1. 可变表 + 审计日志
2. 仅追加的事件存储作为 SSOT；所有状态都是投影/重放
3. 可变表 + 区块链式的外部哈希链

## 备选方案

1. **CRUD + 日志** —— 熟悉；但更正会覆盖真相，谱系重建靠猜，而「谁改了什么」
   最终落进可能不完整的日志。
2. **事件溯源 SSOT** —— 每条事实在源头只被采集一次（BR-07）；更正以补偿事件
   表达；在制品/OEE/谱系都是可重建的投影；留存与导出（NFR-005、CTL-05）变成
   流副本。
3. **哈希链行** —— 增加了防篡改证据，却仍让可变行成为权威；复杂性换不来分叉
   的解决。

## 决策

采用方案 2。执行事件存储是车间事实的唯一真相来源；读模型（在制品、OEE、谱系
图、看板）都是投影，可通过重放重建。更正是引用原事件的补偿事件（BR-07）。

## 后果

- 正面：审计级的完整性由构造保证；重放 = 恢复（读模型损坏是一项运维任务，
  而不是数据丢失）；档案导出是确定性的重放；时序查询自然。
- 负面：存储体量随事件基数增长（用分区 + 留存分层缓解，NFR-005）；团队必须
  学会「不 UPDATE」的纪律（工具中的 BR-07 强制）；投影的最终一致性必须
  在看板上呈现（陈旧度指标）。
- 日后更难更改：事件 schema 的演进需要带版本的载荷与升版器——在 L3 契约中定义。
